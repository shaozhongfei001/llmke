## 1 今天最重要的三件事

### 1.1 指标变好，掩盖了功能变坏

```
15:26  P2-01 修复 -> 加密 PDF 从 23 分钟变成 15 秒静态失败     （指标变好）

```

三个变化都让"耗时"变好，**只有最后一个是真变好**。
判据必须能区分"快速成功""快速失败""快速假结束"。

### 1.2 修 A 弄坏 B：状态机上的隐含前提

`retry_times` 恒 0 的直接原因是**上午那次"修重复派发"**：

```java
// 原：只有当前状态是 RETRY_ING 才 +1
if (RETRY_ING == task.getStatus()) task.setRetryTimes(retryTimes + 1);
// FIX-32 在派发前把状态 CAS 成 DEAL_ING -> 回调时已不是 RETRY_ING -> 永不 +1
```

五个缺陷有同一形状——**都依赖一个从没被写下来的前提**：

| 缺陷 | 依赖的隐含前提 |
|---|---|
| `task-timeout=3600` | 单位是分钟（注释写的是小时） |
| `RETRY_ING` 双计 | 一个状态只承担一种语义 |
| `start_time` 被刷新 | 只表示"开始时间" |
| `depend_on_kb` | 代码读列不读 JSON |
| `retry_times+1` | 回调时状态仍是 RETRY_ING |

**处置**：上线清单增加第四列"**依赖哪个未写下来的前提**"。填写时有两行自己把改动"打回"了（FIX-32、FIX-31b）。

### 1.3 "不存在/成功/为空"是最容易被滥用的信号（族谱 7 条）

| # | 形态 | 表现 |
|---|---|---|
| 1 | `DROP SPACE IF EXISTS kb_9`（漏 `g_` 前缀） | 返回"删除成功"，零删除 |
| 2 | `delete_by_query` | 命中 0 不报错 |
| 3 | nGQL `DELETE VERTEX` 不存在 | SUCCEEDED |
| 4 | `INSERT` 属性名不符 | 静默不插 |
| 5 | `MATCH ... RETURN v.prop` | 恒 NULL（应 `v.<tag>.prop` 或 `FETCH PROP`） |
| 6 | `num_entities` / `static_count` | 含墓碑（108 vs live 1） |
| 7 | `has_collection(coll, using="graph_base")` | `using=` 是**连接别名**，异常被 `except: return False` 吞成"不存在"，HTTP 仍 200 |

**统一判据**：任何"成功/为空/不存在"都不能单独作判据，**必须"同一标识在正确作用域里前后对照"**。

### 4.3 判据设计纪律（本轮新增）

1. **同批 + n≥3**：共享模型端口上，跨批次对比不成立（同一格 0/4、1/3、2/3 都出现过）。
2. **判据要挂"必然被执行"的地方**：`@RefreshScope` 使 `@PostConstruct` 不保证执行 → 播报挂到每 15s 的 `execTask`。
3. **判据要带时间窗**：FIX-31b"启动后 15–30 秒"、P2-01"上传时刻 > 进程 `lstart`"、`PARSE_CONVERT_PATH`"当前进程启动时刻起算"。
4. **判据要对着设计意图**：P0 的判据是"回落是否生效（路径后缀 .docx）"，不是"日志里没有转换失败"。
5. **观测失败不能当健康**：SQL 报错记 FAIL，不吞。

```

④ 引用他人数据必须标"文件名 + 采样条件"，不转述数字
⑤ 进程归属看父链：agent 工具调用 / systemd unit / 人手终端
```

## 7 团队自评（我认为最该带走的三句）

1. **我们不是靠更聪明得出结论的，是靠让每个结论都更容易被推翻。**
   图侧六次归因，前五次都被下一个证据推翻；现在的结论之所以可信，是因为它经过了同批 n=3/n=4 对照，且别人能用脚本重跑。

2. **把"动作完成"当成"目标达成"，是今天所有缺陷的同一个源头。**
   五个人、五种形态：status 200 / status=4 / 单次采样 / del_space 200 / 改了字段。

3. **报警器要像被测对象一样被验证一次。**
   那条"看一眼日志就能判"的判据自己坏了两次，而且两次都被误读成"新代码没加载"。
