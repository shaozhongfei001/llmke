## 1 设计目标与范围


### 1.1 本次要解决什么

现有平台在**能力上并不落后**（506 端点 / 37 表 / 完整三级权限），问题集中在三处：**通用性不足、工程债累积、演进无路径**。本次重构只对准这三处，不追求「推翻重建」。

| 问题 | 现状证据 | 本次对策 |
|---|---|---|
| **通用性不足** | 存储固定 Milvus+ES、分块策略不成体系（有多叉树但无策略选择与回退） | 引入**存储适配层**与**分块策略体系**（借鉴 WeKnora） |
| **工程债** | 双栈联调靠口头约定；契约以截图承载（ENG-01）；埋点命名两套并存（`search_type` vs `search.type`） | **契约优先**（OpenAPI 单一事实源）+ 统一埋点模型 + 统一错误码 |
| **演进无路径** | GraphRAG 与现有能力的关系不清；新能力无插入点 | **旁路式扩展**：检索器插件化，新通路（含 GraphRAG）作为一路接入，不改主链路 |


### 1.2 明确不做什么（范围边界）

评审最容易失焦的地方是「为什么不做某件事」。以下六项**明确排除**，并给出理由，避免评审反复追问。

| 不做 | 理由 | 何时可再议 |
|---|---|---|
| **不改为 Agent 主链路** | 监管场景要求可溯源、可复现、可审计，LLM 自主规划路径不可复现 | 作为「复杂分析类问题」的可选旁路（P5 之后） |
| **不做多租户** | 私有化内网交付，一套部署一个客户；多租户只增加越权面（现有 37 表 0 个 tenant 字段是合理选择，不是缺陷） | 若确定 SaaS 化，需独立立项（架构级） |
| **不统一为单栈** | Python 算法侧（326 文件）是核心资产，重写代价最高；Java 侧企业级权限/事务用 Spring 更成熟 | 见 ADR-01 的否决理由 |
| **不实现 GraphRAG 社区层** | M0 门控未达标，且行业（含 WeKnora）均未落地，属探索性能力 | 门控 1 达标后按 P6 启动 |
| **不重写 deepdoc** | 解析深度（OCR/TSR/XGBoost 版面）是长期积累，重写风险远大于收益 | — |
| **不整体 fork WeKnora** | Go+Vue 与现有团队不匹配；且会丢掉 6 项领域能力 | 通用知识库场景可单独立项 |


### 1.3 复用总原则

| 原则 | 含义 | 适用范围 |
|---|---|---|
| **直接复用** | 代码原样搬迁，仅改包名/配置；不重构内部逻辑 | Python 算法侧全部、Java 工具类与公共模型、37 张表 DDL |
| **移植复用** | 保留业务逻辑，按新工程规范调整分层与接口签名 | Java 六个业务服务（auth / kb / qa / wordfilter / dataquery / gateway） |
| **参考重写** | 只借鉴设计思想，代码重写 | 存储适配层、分块策略体系、融合与埋点（这三处是本次的增量） |
| **禁止改造** | 不动 | deepdoc 解析内核、Nebula/Milvus 驱动、模型推理客户端 |


## 2 架构决策记录（ADR）

本章是评审的核心。每条 ADR 给出背景、决策、备选与否决理由、代价。**若评审只读一章，请读本章。**


### ADR-01 技术栈：保留 Java + Python 双栈

| 项 | 内容 |
|---|---|
| 背景 | 现状 Java 1003 文件（业务）+ Python 326 文件（算法），双栈是最大运维痛点 |
| 候选 A：统一 Python | 算法侧（解析/检索/图/推理）几乎全复用，但需重写 440 个 Java 端点的业务逻辑（权限、知识库、问答记录、事务） |
| 候选 B：统一 Java | 业务侧复用，但需重写 Python 算法侧——**这是核心资产，重写代价最高** |
| **决策** | **保留双栈**，但通过 ADR-02/03/04 三项收敛降低联调成本 |
| 理由 | ① 复用率最高（见第 4 章映射表，约 90% 代码可直接或移植复用）；② Python 在解析与检索生态不可替代；③ Spring 在企业级权限/事务/审计上更成熟；④ 「从头开发」不等于「推翻技术选型」 |
| 代价 | 运维两套构建与依赖；跨栈调试成本 |
| 缓解 | Monorepo 单仓（ADR-02）、契约生成客户端（ADR-03）、算法侧无状态（ADR-04）、统一可观测（第 8 章） |

> **注**：**这条最可能被评审挑战**（「为什么不单栈」）。回应要点：单栈的收益是运维简化，代价是重写一半核心资产。**用一个可控的运维成本，换一次不可控的重写风险，是坏交易**——这与「不 fork WeKnora」的判断逻辑一致。


### ADR-02 工程形态：Monorepo 单仓多模块

| 项 | 内容 |
|---|---|
| 背景 | 现状 Java 与 Python 分仓，契约改动需两边手工同步，是联调问题的根源 |
| **决策** | **单一仓库**，`contracts/`、`java/`、`python/`、`deploy/` 并列；契约变更与两端实现变更在同一个 PR 内完成 |
| 理由 | ① 契约与实现原子提交，杜绝「一边改了另一边没改」；② CodeBuddy 在单仓内可同时看到两端，生成一致性更高；③ CI 可做跨栈契约测试 |
| 代价 | 仓库体积增大；需按目录配置 CI 触发规则（避免改 Python 触发 Java 全量构建） |
| 否决的备选 | Git Submodule / 多仓 + 契约包发布 —— 同步成本更高，且不利于 AI 编码时的全局上下文 |


### ADR-03 契约优先：OpenAPI 3.1 为单一事实源

| 项 | 内容 |
|---|---|
| 背景 | 现状接口契约以截图承载（ENG-01），不可机读、会过期；506 端点中 468 个从未进过文档 |
| **决策** | `contracts/*.yaml` 为**唯一事实源**：服务端由契约生成接口骨架，客户端由契约生成 SDK，CI 校验实现与契约一致 |
| 理由 | ① 一次解决 ENG-01；② 双栈联调靠契约而非口头约定；③ CodeBuddy 可基于契约生成代码，减少自由发挥 |
| 关键约束 | **新增端点必须先改 contracts/**，否则 CI 拒绝（见 8.7 禁止事项第 8 条） |
| 迁移策略 | 以《源码接口契约.xlsx》506 端点为底稿，分批转写为 YAML；先转已确认在用的（约 380），废弃的先标注不转 |


### ADR-04 算法侧无状态 + 不直连业务库

| 项 | 内容 |
|---|---|
| 背景 | 现状算法服务通过 Nacos 拿配置、直连 ES/Milvus/MySQL。直连业务 MySQL 会让算法侧隐式持有业务逻辑 |
| **决策** | 算法侧**只做无状态计算**：入参 → 计算 → 出参。**禁止直连业务库**（`knowledge_base` / `user_*` / `dialogue` 等 37 表）；只允许连**索引存储**（ES/Milvus/Nebula） |
| 理由 | ① 边界清晰后双栈联调成本可控；② 算法服务可独立扩容与替换；③ 权限判断只在业务侧，避免越权风险 |
| 例外 | 结构化服务（`index_structure_service`）需读业务 MySQL 的动态表——通过**受限数据源**（只读账号 + 表白名单）实现，不视为违反 |
| 落地检查 | CI 增加静态检查：`python/**` 中出现 `knowledge_base` / `user_info` 等业务表名即失败 |


### ADR-05 检索链路：固定流水线，不做 Agent 主链路

| 项 | 内容 |
|---|---|
| 背景 | WeKnora 采用 Agent 化（154 文件 + 沙箱 79 文件），LLM 自主调用 30+ 工具 |
| **决策** | **保留固定流水线**：query 理解 → 多路召回 → 融合 → 精排 → 生成。每一步可埋点、可复现 |
| 理由 | ① 监管问答必须能解释「这个答案是怎么来的」；② 流水线每步可单独评测，Agent 路径不可枚举；③ 既有 506 端点全部围绕流水线设计，改范式等于全部重写 |
| 代价 | 复杂分析类问题（多步取数+计算+成文）能力弱 |
| 缓解 | P5 引入**受限 Agent 旁路**：仅在 `query_type=analysis` 时启用，工具白名单（knowledge_search / database_query / data_analysis），**不开放沙箱代码执行** |


### ADR-06 存储适配层（借鉴 WeKnora）

| 项 | 内容 |
|---|---|
| 背景 | 现状 Milvus + ES 写死；客户环境若只有 pgvector / OceanBase 则无法适配。WeKnora 支持 6 种存储引擎 |
| **决策** | 引入四个抽象接口：`VectorStore` / `FullTextStore` / `GraphStore` / `StructuredStore`；默认实现 Milvus / ES / Nebula / MySQL，预留 pgvector / OpenSearch |
| **关键取舍** | **抽存储，不抽链路**。仅抽象底层存储操作，**不**引入 WeKnora 的「事件式检索器插件」（`PluginSearchEntity`）——后者会让「哪条通路被激活」不可预测 |
| 理由 | ① 客户环境适配是真实需求；② 只抽象存储，业务逻辑与可解释性不受影响；③ 4 个子服务（向量/全文/结构/图）共享同一套 CRUD 语义，减少重复 |
| 代价 | 抽象层需谨慎设计，过度抽象会导致「为了通用牺牲性能」 |
| 约束 | 抽象接口只到「读写删查 + 相似检索」粒度，**不抽象具体参数**（如 Milvus 的 index_type 作为实现细节下沉） |


### ADR-07 分块策略化（借鉴 WeKnora）

| 项 | 内容 |
|---|---|
| 背景 | 现状有自研「多叉树分块」与层级切分，但无策略选择、无自适应、无回退；换一类文档就要改代码 |
| **决策** | 建立策略体系：`profiler`（探测文档特征）→ `strategy`（auto / heading / heuristic / recursive / **multipath_tree**）→ 产出 chunk。**把自研多叉树提升为策略体系中的一等公民** |
| 理由 | ① 借鉴的是「策略化」这个结构，不是照抄 5 个策略；② 多叉树是既有优势，纳入体系才能复用；③ 解析质量决定下游上限（含未来社区摘要） |
| 代价 | 策略切换可能引入回归（同一文档换了策略，chunk 数变化 → 索引需重建） |
| 缓解 | **策略变更视为索引配置变更**，走「新建索引 + 灰度 + 切换」而非原地改；且 `profiler` 结果落库（见 5.2 `chunk_strategy_profile`），可追溯每份文档为何选了该策略 |


### ADR-08 多版本：索引按有效版本，检索保留多版本

| 项 | 内容 |
|---|---|
| 背景 | 现状有「多版本并行召回」（`multi_version_dict`），是监管刚需；但对建图是负资产（同一实体跨版本合并会导致摘要自相矛盾） |
| **决策** | **索引层按有效版本建图**（只有现行有效版本进图谱）；**检索层保留多版本**（向量/ES 仍可召回历史版本，供「历次修订有何变化」类问题） |
| 理由 | ① 图谱用于「现状问答」，混入废止版本必然出错；② 历史对比问题走全文通路即可，不需要图；③ 保留既有能力不倒退 |
| 影响 | 图谱与全文的覆盖范围不一致，需在**接口返回中显式标注** doc_version 与 is_effective，避免调用方误用 |


### ADR-09 GraphRAG 仅作旁路，且门控触发

| 项 | 内容 |
|---|---|
| 背景 | M0 门控未测；行业（含 WeKnora）均未落地社区层；且社区跨文档聚合与三级权限冲突 |
| **决策** | GraphRAG 定位为**第 5 路检索器**，通过 `enabled_community` 开关控制，默认 false；**不进入主链路**，不改动现有 6 路 |
| **权限硬约束** | **社区检测必须在权限域内独立执行**（按知识库 × 授权主体切分图），摘要不得跨权限域生成。**不接受「事后过滤」**——摘要一旦生成，信息已混合，无法拆分 |
| 启动前置 | ① M0 门控 1 达标（基线要点覆盖度 < 50%）；② 权限切分方案签字；③ 版本策略确认（ADR-08） |
| 代价 | 按权限域切分后，社区规模变小、数量变多，摘要质量下降——**此代价必须在立项时接受** |

> **注**：**ADR-09 的权限约束是本次设计最重要的安全决策**。若评审认为「先做再补权限」，应直接否决——事后过滤在信息论上不可行，这不是工程排期问题。


### ADR-10 网关与鉴权统一

| 项 | 内容 |
|---|---|
| 背景 | 现状 `rag-gateway`（8 文件）与部署文档中的 Kong 并存，职责边界不清 |
| **决策** | 两层职责分离：**Kong 做流量网关**（路由、限流、TLS、日志），**`rag-gateway` 做业务网关**（鉴权、租户上下文、审计、灰度分流） |
| 理由 | ① 流量治理与业务鉴权的变更频率不同，混在一起会导致每次鉴权改造都动网关配置；② Kong 的插件生态适合流量层；③ 业务网关贴近 Spring 生态，便于接入三级权限 |
| P0 待产出 | 一张「哪些能力在 Kong、哪些在 rag-gateway」的职责矩阵，作为 P1 的输入 |


## 3 目标架构


### 3.1 分层与依赖方向

**依赖必须单向**：`接口层 → 应用层 → 领域层 → 基础设施层`。跨层调用在 CI 中静态检查拦截。

| 层 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| 接口层（interfaces） | HTTP 入口、参数校验、DTO 转换 | 应用层 | 直接依赖基础设施（如直接调 Mapper） |
| 应用层（application） | 用例编排、事务边界、权限校验 | 领域层、基础设施接口 | 写 SQL、拼路径 |
| 领域层（domain） | 实体、值对象、领域服务、仓储接口 | 无（纯 POJO） | 依赖 Spring 注解以外的框架 |
| 基础设施层（infrastructure） | 仓储实现、外部客户端、存储适配 | 领域层接口 | 被上层直接引用具体类 |


### 3.2 服务清单

保留现有 9 个 Java 模块 + 5 个 Python 服务；**合并 1 个、新增 0 个**（不新增服务，避免运维面扩大）。

| 服务 | 语言 | 职责 | 来源 | 端点数 |
|---|---|---|---|---|
| gateway | Java | 业务网关：鉴权、上下文、审计、灰度 | rag-gateway | — |
| auth-service | Java | 用户/角色/权限/部门/机构组/接口资源 | rag-auth-service | 138 |
| kb-service | Java | 知识库、文件、解析任务、模型、标签、**图谱查询（合并）** | rag-index-service + rag-graph-service | 182 + 17 |
| qa-service | Java | 问答、对话、反馈、检索配置、API Key | rag-qa-service | 68 |
| wordfilter-service | Java | 敏感词库与命中检测 | sensitive-words-service | 12 |
| dataquery-service | Java | 数据库直连与表结构探查 | tools/tools-database | 23 |
| alg-parse-service | Python | 文档解析（OCR/TSR/版面） | alg_doc_parse_service | 11 |
| alg-llm-service | Python | 推理、FAQ 生成、润色、多模态 | alg_llm_inference_service | 14 |
| alg-retrieval-service | Python | 多路召回、融合、精排 | alg_retrieval_service | 4 |
| alg-index-service | Python | 向量/全文/结构/图 四类索引 | index_data_service | 14 + 10 + 5 + 7 |
| version-service | Python | 代码版本查询 | index_data_service/version_service | 1 |

> **注**：**合并 `rag-graph-service` 到 `kb-service`** 的理由：该模块仅 18 个 Java 文件、3 个 Controller，职责是「查 Nebula 的节点与边」，本质是知识库的读操作，独立成服务带来部署与调用开销而无独立扩缩容价值。**这是唯一一处服务合并**，其余保持不动以最大化复用。


### 3.3 部署拓扑

保持现有形态：K8s + Nacos + Kong。**不引入新中间件**——本次所有增量（存储适配、分块策略、审计）均在应用层完成，无新增基础设施依赖。这一约束可显著降低上线风险。

| 步骤 | 动作 | 回滚方式 |
|---|---|---|
| ① 结构同步 | 用现有 37 表 DDL 初始化新库（Flyway/Liquibase 版本化） | 库级快照 |

## 6 接口契约设计


### 6.1 契约规范

| 项 | 规范 |
|---|---|
| 规范版本 | OpenAPI 3.1，YAML 文件按域拆分（`contracts/{auth,kb,qa,retrieval,index,common}.yaml`） |
| 路径风格 | **保持现状**（`/retrieval_documents` 而非 RESTful 化），理由：兼容优先，RESTful 改造无收益且破坏调用方 |
| 错误码 | `{域}-{3位数字}`，域：`AUTH` / `KB` / `QA` / `RET` / `PARSE` / `STORE` / `GATE`；须在 `contracts/common/errors.yaml` 登记 |
| 分页 | 统一 `pageNo` / `pageSize`，响应 `{total, list}` |
| 幂等 | 写操作支持 `Idempotency-Key` 头；索引类操作以 `(kb_id, file_id, config_version)` 幂等去重 |
| 鉴权 | `Authorization: Bearer <token>`；内部服务间用 `X-Internal-Token` |
| 追踪 | 全链路 `X-Trace-Id`，网关生成，逐跳透传 |


### 6.2 召回请求/响应统一模型（关键设计）

现状 6 路通路的返回字段命名不一致（`search_type` 与 `search.type` 并存，已确认会导致分通路统计漏算图谱）。本次**统一为一套模型**，这是埋点准确性的前提。

| 字段 | 类型 | 说明 |
|---|---|---|
| `search_type` | enum | **唯一命名**：`es` / `milvus` / `graph` / `table` / `faq` / `web` / `database` / `community` |
| `score` | float | 融合后得分；各通路原始分放在 `raw_score` |
| `rank` | int | 在通路内的原始排名 |
| `source` | string | 源文件 |
| `offset` | int[2] | 字符区间（左闭右开，码点单位） |
| `chunk_pk` / `entity_pk` | string | 命中主键，供溯源回链 |
| `doc_version` / `is_effective` | string / bool | **ADR-08 要求**：标注版本与是否现行有效 |
| `perm_scope` | string | 命中内容的权限域（用于越权兜底校验） |

> **注**：**`search_type` 统一为唯一命名，废除 `search.type`**。这是一处**破坏性变更**，因此需要：① 兼容期同时读取两个字段；② 前端与调用方在同一版本内改造；③ 兼容期不少于一个发布周期。这一点必须在评审时被记录，不能悄悄改。


## 7 核心链路设计


### 7.1 索引链路

1. **接收**：`kb-service` 创建 `file_parse_task`，投递解析请求。
2. **解析**：`alg-parse-service` 执行 OCR/TSR/版面分析，产出结构化文本（含标题层级）。
3. **分块**：`profiler` 探测文档特征 → 选策略（auto/heading/heuristic/recursive/multipath_tree）→ 产出 chunk，`chunk_strategy_profile` 落库。
4. **写入**：`alg-index-service` 经 storage 抽象层并行写入向量（Milvus）/全文（ES）/结构（MySQL）/图（Nebula，**仅有效版本**）。
5. **回执**：任务状态回写 `file_parse_task`，失败进入重试（`re_embedding_retry_task`）。


### 7.2 召回链路

1. **入口**：`/retrieval_documents` 接收 `QARetrieveConfig`（保留现有字段，新增 `rerank_strategy`、`chunk_strategy_version`）。
2. **并行召回**：按开关并行执行 6 路（关键词 / 向量 / 图谱 / 表格 / FAQ / 联网 / 数据库），**每路独立超时与降级**。
3. **融合**：默认 RRF；保留加权融合作为可选（`fusion_mode` 参数），便于对比。
4. **精排**：`bge-reranker-v2-m3`，Top-N 截断。
5. **补全与溯源**：邻近块补全（`adjacent_chunk_num`）+ offset 回填。
6. **埋点**：`pipeline_trace` 记录每路耗时/命中/降级，支撑分通路归因。

> **注**：**「每路独立超时与降级」是本次新增的可靠性约束**。现状是串行 try-catch，任一路异常可能影响整体；改为并行 + 独立超时后，单路故障不外溢。这条改动直接消除了现有代码中「graph 查询异常直接 return 空列表」这类隐患的放大效应。


### 7.3 问答链路

- `/retrieval_qa`（保留路径，内部重构）→ 组装 prompt → 流式生成（SSE）。
- **引用强制**：每条结论必须携带 `source + offset`，无出处的结论在响应中标记 `unverified`。
- **FAQ 优先**：`faq_score_threshold` 命中时直出，不再走生成（节省时延）。
- **表格与数值**：表格走 `table_summary_`/`table_chunks_`；数值类问题优先 `dataquery-service`（SQL 比向量准一个量级）。


### 7.4 GraphRAG 旁路（P6，条件触发）

设计上**只预留插入点，不实现**。启动条件见 ADR-09。若启动，链路如下：

1. **索引期**：在**权限域内**对有效版本图执行 Leiden 层级聚类 → 逐社区生成摘要（自底向上）→ 写入 `community_report`（Milvus 集合）+ `graph_community`（元数据，含 `perm_scope`）。
2. **查询期**：`query_type=global` 时启用 → 检索社区摘要 → map-reduce 汇总 → **引用回链到原文而非摘要**。
3. **降级**：任一步失败则回退到现有 6 路，不阻塞问答。

## 9 实施路线

### 9.2 并行与依赖

- P0 是所有阶段的前置，不可并行。
- P1 与 P2 **可并行**（一个管数据与权限，一个管解析与索引，互不依赖）。

- P5 各项**可并行**，但「检索器扩展」依赖 P3 的 storage 抽象完成。
- P6 独立，条件触发后可与其他阶段并行（若资源允许）。

## 11 风险与待决


### 11.1 风险

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| D-01 | **Python 后端取自 dev 分支**（B-09） | 复用代码可能与线上不一致，移植后行为偏差 | P0 期间向研发索取 dev↔prod diff；以发布制品为准 |
| D-02 | **契约转写工作量被低估** | P0 延期，阻塞全部后续阶段 | P0 只转「已确认在用」的约 380 个；其余按需增量转写 |

| D-05 | **双栈联调成本高于预期** | 进度失控 | ADR-03/04 的契约与边界约束是主要防线；P1 结束时做一次联调压力测试 |

| D-07 | **GraphRAG 权限方案被简化** | 越权泄露 | ADR-09 的 `perm_scope` 非空约束 + 检测任务拒绝写入；不提供「事后过滤」选项 |

> **注**：**D-06 值得单独强调**：重构最容易犯的错是「把旧代码原样搬过来，连 bug 一起搬」。已确认的 B-10（图谱空间名疑似双重前缀 `g_g_`）就是一个例子——若不复核直接移植，新系统会在同一个地方再挂一次。**移植不等于免检。**

## 12 评审关注点（自评）

以下是本次设计**最可能被质疑的六点**，连同我的回应一并列出。这能提高评审效率，也便于识别真正的薄弱环节。

| 编号 | 可能的质疑 | 我的回应 | 薄弱程度 |
|---|---|---|---|
| R-01 | 为什么保留双栈，不统一？ | 重写一半核心资产换运维简化，是坏交易；且已用 Monorepo + 契约 + 边界约束三项收敛成本（ADR-01） | **中等**：若团队只有 1~2 人，单栈可能更优，需按实际人力复核 |
| R-02 | 为什么不直接 fork WeKnora？ | 会丢掉 6 项领域能力；且 Go+Vue 与现有团队不匹配（见对比评估第 7 章） | 低 |
| R-03 | 506 端点如何保证不丢功能？ | 以 `源码接口契约.xlsx` 为清单逐项核对；不删在用端点；合并只在实现层（4.3 节） | 低 |
| R-04 | 分块策略化会不会引入回归？ | 会。因此策略变更走「新建索引 + 灰度」，且 `chunk_strategy_profile` 可追溯每份文档的选择依据（ADR-07） | **中高**：这是真实风险，需在 P2 留出回归窗口 |
| R-05 | GraphRAG 与权限如何解？ | 社区检测在权限域内独立执行，`perm_scope` 非空约束；不接受事后过滤（ADR-09） | 低（安全上清晰），但**会降低摘要质量**，需产品接受 |
| R-06 | 21 周估算依据？ | P0~P5 按阶段拆分，前提是复用成立（第 4 章映射表）；若复用率低于 80%，周期需重估 | **中高**：复用率是本估算的唯一杠杆 |

> **注**：**我认为最需要外部意见的是 R-04 与 R-06**：前者是真实的技术风险（分块变更必致索引重建），后者是估算的杠杆点（复用率）。其余四点属于决策取舍，逻辑自洽即可。
