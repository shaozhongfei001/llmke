### 本次独立实测：§3.0 的命令存在漏项

临时 Git 仓库的输入：

```text
 D deleted.txt
R  rename-old.txt -> rename-new.txt
 M same.txt
 M "with space.txt"
?? data/
```

复跑同等逻辑，仅输出 `same: same.txt`。改用 `git status --porcelain=v1 -z --untracked-files=all` 后，能取得删除项、重命名的新旧路径、带空格的原路径及 `data/sample.json`。此实验验证了漏项机制；**无法由此判定 LLMKE 未解释的 4 项是哪几项**。目录展开后实际路径数也可能大于 36。

## 三、怎样证明 r12 确实无需再贡献代码

按四层证据验证，最终比较对象是**将进入 main 的候选提交**。即使 r12 的修复全在 v2，只要当前 main 尚未吸收这些修复，就不能说 r12 相对当前 main 没有增量。需要证明的是：**合入经核验的 v2 变更后，r12 没有额外有效源码差异需要补入**。

| 层次 | 要回答的问题 | 判据 |
|---|---|---|
| Git 历史 | 本地 r12 和拟删除远端分支是否有需要保留的提交？v2 HEAD 是否还有候选必须吸收的已提交变更？ | 固定四类引用：本地 main、v2 HEAD、r12 HEAD、远端目标分支。记录共同祖先与各自独有提交。已合入和归档保全分别标明。 |
| 工作区 | 36 条来源记录的真实内容是什么？ | 分别检查暂存和未暂存差异，展开未跟踪目录；核对新增、删除、重命名、文件模式和链接。保留状态行到路径的映射。单列被忽略但要保留的配置和数据。 |
| 有效内容 | 候选是否保存 r12 的每个有效修复？ | 相同文件证明候选里也包含相同变更；不同文件逐差异块审阅和验证。#6/#8/#25 优先保留 v2 版本，但须证明保留各自旧修复与新修复。部署配置按正式部署方案迁移。 |
| 可运行结果 | 修复和启动路径是否在候选环境真正生效？ | 对同一候选提交运行必要的编译、摄取、检索、两知识库路由、引用回查及启动场景。结果绑定提交、配置和制品。 |

台账建议最小字段：`原编号｜原状态｜旧/新路径｜暂存/未暂存｜分类｜有效差异｜候选提交/路径｜处置｜证据`。

处置使用：`候选已覆盖`、`补入最小有效差异`、`部署侧迁移`、`归档退出`、`待核`。未完成逐项核对之前，建议改写原结论为：

> 已比对的路径支持“由 v2 单路集成”的方案假设；r12 是否无额外源码差异，待完整对账及候选验收确认。部署配置和运行数据单独迁移与验收。

## 四、v2 的 131 项怎么切提交

先确认 v2 HEAD 相对 main 的已提交差异，再处理其暂存区和工作区。以核验时的 main 提交创建一条短期候选分支，例如 `integrate/converge-main`。根据台账选择补丁和已提交变更；使用显式路径或差异块暂存。提交前看暂存差异和文件清单。

建议约 **4–7 个提交**，按真实依赖合并或拆分下列单元，数量不作为考核指标：

| 单元 | 建议内容 | 提交验收 |
|---|---|---|
| 1. 公共修复与基础配置 | 独立的检索参数、ID 类型、DAO／日志兼容、默认配置；相互依赖的改动放同一提交。 | 受影响模块可编译；具体修复有针对性回归。 |
| 2. DOC2MD 摄取闭环 | 以 `#11 → #35 → #17/18 → #19` 检查依赖，将 DTO、客户端、入口、回调及测试组成完整单元。 | 文档摄取、回调成功与失败、开关关闭行为均符合约定；避免提交不能编译的中间态。 |
| 3. 图谱和检索接入 | 知识库路由、图谱代理、图检索开关与引用相关修复。#6/#8/#25 审核后保留 v2 正确版本。 | 两个知识库不串图；权限范围、真实图检索与回退、引用可回查。 |
| 4. 前端主题和图谱工作台 | 对照实际已实现的 SPECTRA 主题及图谱页面差异；相互独立时拆成两个提交。 | 前端构建、产品路由和关键交互通过；结果与现有真实接口一致。 |
| 5. 发布与交接 | 必需启动脚本、配置模板、证据索引、回退说明；运行配置和数据归部署侧管理。 | 在隔离环境从固定提交构建、启动并回退；包中不混入本地数据、密钥、日志和备份。 |

每个提交说明写清改动目的、涉及的 `Lx / TASK-ID`、验证和必要依赖；回退有依赖的变更时按相反顺序回退。有关 #9 的端口外提、#36 的启动策略放入实际消费它们的单元，不预设改动一定需要。将 131 条状态记录映射到提交／归档／排除项；保留必要的 L1–L13 证据引用，避免为保留编号而重复历史产物。

提交拆分的硬判据是**每个提交可构建，差异可审，回退影响清楚**。只有工作单元与 loop 一一对应时才按 loop 切。候选提交整体通过项目当前适用门禁后合入；main 如有新变更，先更新候选并复核受影响证据。

## 五、推荐的收敛顺序

| 步骤 | 动作 | 放行条件 |
|---|---|---|
| 1. 固定起点 | 同一次采样记录三个实际 HEAD、工作树根、共同 Git 目录、状态和远端引用。检查当前主分支及适用的合并规则。 | 本地与远端的比较对象清楚；变更期间相关写入已协调。 |
| 2. 归档并实恢复 | 保全 v2、r12 及必要 stash／Git 对象；归档放到待清理目录之外。另做生产数据与配置的适当备份。 | 从对应基点恢复暂存、未暂存和未跟踪项，清单与哈希对得上；必要数据可恢复。 |
| 3. 单路构建候选 | 从 main 起步，吸收 v2 的已核准提交与工作区变更。r12 默认只核对；发现真缺口再补最小差异。 | 131 项与 36 项分别有完整去向；通过针对性验收，无冲突遗漏。 |
| 4. 正常合入 main | 审查实际候选差异，走当前分支保护与 QA 流程。 | main 包含受验收的最终代码和追溯记录；如合并结果不同于候选，补验证最终结果。 |
| 5. 切换发布路径 | 从明确的 main 提交构建制品，使用独立发布目录与持久化数据目录。记录旧制品、配置和恢复方案；在测试环境验证，按现有发布授权实施切换。 | 冷启动、摄取、检索、图谱、引用和回退通过；定时任务、进程、配置及挂载不再依赖旧工作树。 |
| 6. 退役旧目录与分支 | 再核对实际引用、进程和待保留文件；按清单清理旧工作树，使用 `git worktree remove`，优先用 `git branch -d` 删除已合并本地分支。远端只处理逐个核实的分支。 | 可恢复归档已验证，分支有效内容已保留。若 `-d` 拒绝，核对未合入提交及上游设置；确需强制删除的对象单独裁定。 |

目标形态：**一个仓库、一个常驻开发工作树、一个长期主分支 main**。短期任务分支完成后清理。历史保存在 Git 及可恢复归档中；生产运行目录保存固定版本的制品，配置与数据落在明确的持久化位置。生产不随开发工作树变化。

最容易造成不可逆损失的步骤，是恢复验证和生产脱离之前强制移除脏工作树、运行 `git clean -fdx` 或直接删除目录。清理目标是减少日常维护副本，归档和数据保留按实际恢复需求执行。

## 七、原机只读核验入口

执行方在真实仓库所在主机运行。以下命令用于补证，不创建提交、不清理目录、不修改分支。保存输出时保留退出状态；对外只提交脱敏清单和验证结果。

```bash
set -euo pipefail
llmke_review_root=/home/szf/data/dev
llmke_main_dir="$llmke_review_root/llmke"
llmke_v2_dir="$llmke_review_root/llmke-v2"
llmke_r12_dir="$llmke_review_root/llmke-r12"

git --no-optional-locks -C "$llmke_main_dir" worktree list --porcelain
for llmke_tree in "$llmke_main_dir" "$llmke_v2_dir" "$llmke_r12_dir"; do
  git --no-optional-locks -C "$llmke_tree" rev-parse --show-toplevel
  git --no-optional-locks -C "$llmke_tree" rev-parse --path-format=absolute --git-common-dir
  git --no-optional-locks -C "$llmke_tree" rev-parse --verify 'HEAD^{commit}'
done
llmke_main_oid=$(git -C "$llmke_main_dir" rev-parse --verify 'refs/heads/main^{commit}')
llmke_v2_oid=$(git -C "$llmke_v2_dir" rev-parse --verify 'HEAD^{commit}')
llmke_r12_oid=$(git -C "$llmke_r12_dir" rev-parse --verify 'HEAD^{commit}')
git -C "$llmke_main_dir" rev-list --left-right --count "$llmke_main_oid...$llmke_r12_oid"
git -C "$llmke_main_dir" rev-list --left-right --count "$llmke_main_oid...$llmke_v2_oid"
git -C "$llmke_main_dir" log --oneline "$llmke_main_oid..$llmke_r12_oid"
git -C "$llmke_main_dir" log --oneline "$llmke_main_oid..$llmke_v2_oid"
git -C "$llmke_main_dir" stash list --format='%gd %H %gs'

# 查看远端实际引用，直接保留输出；失败要报错，不换算成 0。
git -C "$llmke_main_dir" ls-remote --refs origin refs/heads/main \
  refs/heads/feature/R12-real-rag refs/heads/feat/spectra-theme
```

用下面的清单替代 §3.0 的 shell 分词循环。`XY` 的两列分别记录暂存区、工作区状态；在 `-z` 输出中，重命名或复制先给新路径、再给旧路径。

```bash
python3 - "$llmke_v2_dir" "$llmke_r12_dir" <<'PY'
import json
import os
import subprocess
import sys

for tree in sys.argv[1:]:
    for scope in ('normal', 'all'):
        raw = subprocess.check_output([
            'git', '--no-optional-locks', '-C', tree, 'status',
            '--porcelain=v1', '-z', '--untracked-files=' + scope,
        ])
        fields = iter(raw[:-1].split(b'\0') if raw else [])
        rows = []
        for field in fields:
            xy = field[:2].decode('ascii')
            row = {'xy': xy, 'path': os.fsdecode(field[3:])}
            if 'R' in xy or 'C' in xy:
                row['old_path'] = os.fsdecode(next(fields))
            rows.append(row)
        print(json.dumps({'tree': tree, 'scope': scope, 'count': len(rows)}))
        for row in rows:
            print(json.dumps(row))
```
