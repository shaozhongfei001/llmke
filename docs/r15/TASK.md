### 1.4 V1.1补充：知识库是领域边界，产品交付必须体现跨文档知识组织

本节落实用户2026-10-30反馈：进入既有知识库的“图谱增强”后，用户主要看到按文件解析/展示，未感知到分散资料形成关联知识。本节并入正在执行的R15，不重开一个空白轮次；保留已有有效成果，更新当前任务队列和同一Goal的验收条件。

**产品含义**

1. 用户自定义知识库是知识领域和管理边界；对当前用户可见的有效文档版本，建立逻辑统一的领域知识图谱。
2. 文档是事实来源，chunk是抽取单元；逐文件抽取的结果须归一到同一受控领域图中。
3. GraphRAG社区是在领域图内识别出的实体关系簇，可有多层。一个知识库可以包含多个社区，一个社区可由多文档支持，一个文档也可贡献多个社区。
4. 不将“知识库ID”“文档ID”“社区ID”互相替代，不把“文件”直接当算法社区。
5. 逻辑统一不强制只有一个物理空间，也不把无权限或非现行资料混入当前图；继承W03的授权域和代次边界。
6. 相同真实实体在不同文档中复用canonical身份，跨文档事实围绕它形成可查询的关系和证据；同名不同主体不误合并。
7. 不要求所有文档强行连通，不为让图好看而生成无原文支持的关系。统一图可以包含真实的多个连通分量。

**页面与操作要求**

- “图谱增强”须提供知识库级建设概览，明确当前范围、文档覆盖、未完成/失败、当前发布代次、社区报告与问答就绪状态。
- 用户不选择单个文件，也能直接进入“知识库图谱”，查看当前授权范围的统一知识结构。
- 提供“主题社区”视图：层级、主题、实体、支持文档/事实、报告及证据。检测未完成时明确状态，不用文件列表冒充社区。
- “来源文档”保留逐文件解析、重试和子图能力；文件视图是来源过滤或高亮，保持与统一图相同的实体身份及代次。
- 能选择实体查看跨文档邻域、来源和关系；在已知关联文档之间找到有真实支持的路径，并从路径或报告进入问答。
- 大图采用层级概览、搜索、分页/有界展开；图索引应覆盖规定范围，屏幕不必一次加载全部节点。显示范围、截断/采样、总量口径要明确。
- “单文件已抽取”“整库图已发布”“社区报告就绪”“global可用”分别表示，不用一个绿色解析状态替代。

**当前源码核对与复用要求**

2026-10-30核对GitHub main=c51ae46e2d01fc63ff31e23a5d95c31dd9b79a3c：

- GraphBox.tsx:462–465的showGraphHandler使用allGraph；851–861有页面顶部“可视化图谱”按钮。
- GraphBox.tsx:753–762的文件行入口使用fileId+subGraph。
- GraphCanvas.tsx:62–74分别调用库级wholeGraphSearch与文件相关subGraph。
- graph_community.py:30–48按空间读取关系后检测社区。

这些仅证明入口/算法代码存在，不能证明现场部署、实体融合、全库覆盖或社区问答有效。TL须实际对账点击入口、网络请求、查询范围、canonical身份、原始支持和运行版本。优先复用、补通已有库级入口及存储能力，避免重造平行图平台。

9. 原则上优先评估按KB/域/代次分离物理产物，以适配当前大量无过滤查询；先实测空间数量和双代资源。若采用属性方案，身份、边、每条查询和各投影必须全覆盖隔离。
10. staging完整构建并校验后切active；构建失败不破坏仍安全有效的旧代；授权变化不得继续使用已不安全旧代。
11. 从原文和有效快照重建遗留受损图，迁移先在恢复副本验证。不能给旧数据统一补代次标签后宣布迁移完成。
12. 图谱页能显示整库构建状态、当前代次、社区就绪情况、失败原因、重试入口及数据更新时间；落实§1.4的知识库图谱、主题社区与来源文档视图，逐文件解析只是来源任务。

通过：空白新KB经真实页面上传多文档后，无手工生成脚本即可得到可查询社区；更新、删除、切换、回滚和撤权满足A09/A10/A14。

### W04｜社区层级、报告与真正的广域汇总：F08、F13、G5–G9

1. 落实原设计的层级社区能力。优先原Leiden路线；保留其他算法须有同语料的质量/成本对照和已授权技术差异裁决。
2. max_level与实际层级一致，保存父子关系、成员、范围、代次和算法参数；不能参数写2而实现仅两层。
3. 小社区与孤立事实保留可检索覆盖；“不生成长摘要”不等于删除事实。
4. 不把无向聚类投影中的边当有向业务事实，不丢失原断言和来源身份。
5. 报告包含主题、范围、结构化findings、支持事实/来源、覆盖和截断信息；不能截前60条却称全部事实。
6. 区分“聚焦社区搜索”和“广域综合”：前者可混合召回+重排；后者覆盖选定层级报告、分批Map再Reduce，记录覆盖和省略原因。
7. Map可以采用经验证的语义或结构方法，必须处理无实体全名的主题问、同义改写与跨社区综合；不能继续只靠少量词法规则承担全部global。
8. 不把简单替换向量模型当覆盖问题已解决；最终Reduce须消费真实报告/事实分析结果及证据。
9. resolution、社区规模和报告预算基于固定语料、目标题及资源实验选择，保存对照；不宣称某个默认值普遍适合银行。
10. 首版可增量抽取、整批重算社区；先使完整重建正确，规模实测需要后再加增量聚类。
11. 稳定社区逻辑身份与发布版本分开，重建幂等，旧报告不会重复计数或混入当前。
12. 导出最终同代完整报告，逐项核验主题、关键数值、约束与来源，关闭“只有7条数量没有质量依据”的缺口。

通过：无实体名的广域题、跨文档多跳题、同义问法和干扰语料均有真实结果；GraphRAG贡献通过通路追踪与受控对照说明。

### W05｜统一两条问答入口、原文证据及流式行为：F04、F06

## 4. 阶段与 Loop Engineering

每个Loop使用相同循环：

**固定本切片预期 → 建立有效失败/当前行为证据 → 最小生产实现 → 组件与消费者验证 → 真实集成 → QA返回缺陷 → 修复复验 → TL确认退出 → 自动进入下一阶段。**

本任务只安排一个连续执行窗口，内部包含多个Loop，不要求用户逐阶段发新提示词。

| 阶段 | 实际成果 | 退出条件 | 不通过时下一动作 |
|---|---|---|---|
| L0 接手与启动 | 当前候选/环境事实、任务队列、真实前端路径、最小接续入口；开始复现关键缺陷 | 资源/所有权明确，首批代码任务已派发；至少一个有效失败判据或已有修复复验 | 缺项转具体资源任务；继续能施工部分，不返回纯盘点 |
| L1 图事实可靠 | W01/W02与写入证据；B/C/E并行准备下游 | A01–A06相关事实在真实存储验证，错误方向/覆盖/误推导不能放行 | A缩小复现修根因；下游使用已对齐接口继续实现 |
| L2 整库构建发布 | W03/W04，空KB经页面到可发布社区与库级图谱 | A07/A09/A10及A17的图谱/来源视图子项通过，同域同代、失败不发布，完整报告可查 | 保留安全旧代，修构建/状态；不靠脚本补建作通过 |
| L3 用户GraphRAG与证据 | W05/W06；一条从库级知识结构到答案和原文的跨文档旅程 | A08/A11/A12/A13及A17整体通过，两入口语义一致，关键结论全部有支持 | 定位图事实、召回、Map、Reduce、消费或引用具体故障层再修 |
| L4 故障、回归与实际资源 | W06/W08，完整能力回归；稳定候选运行观察 | 权限/撤权、故障/并发/预算与受影响C01–C20验收通过，无开放交付缺陷 | 精确重开受影响项，重新验证；长观察后台运行 |
| L5 离线交付与授权发布 | W07完整候选、干净实装/恢复回退、目标发布 | A14–A16及第9节终态满足 | 缺依赖补包并重装；仅真正外部发布依赖可转暂停 |

阶段关系控制验收与发布依赖，不阻止无冲突工作提前进行。离线准备、前端、QA、环境实装从L0开始并行，最终候选必须重新验收。

### 4.1 推进节奏

- 首个工作时段形成实际代码/测试或部署修复，不停留在任务书和治理资料。
- 每完成一个可集成小切片就合并与复验，避免各角色最后一次性提交。
- 每次变更选择相关测试；最终候选执行完整必选验收。Stop/续跑检查不重复全套题或24小时观察。
- 必需合同与控制面变更集中处理；需要冻结时按现有流程进行，先完成验收实验，再冻结并运行正式门禁。
- 发现已测试候选有缺陷必须修复，相应证据按真实依赖失效并重跑，不能为保住绿色而留下缺陷。
- 文件增加、日志增长、提交数与运行时长不作为产品进度。

| A15 完整KB回归与资源 | 核验C01–C20及原必选扩展；执行既定容量和持续运行 | 必选实际使用流程成立；无空结果/跳过假绿；真实模型参与；资源结果可复算 |
| A16 离线与发布 | 候选包干净离线复建实装，核对全量/差分，再在既有授权目标验证 | 完整源码/依赖/模型/配置与运行一致；入口可用；发布状态、签收状态如实区分 |
| A17 知识库级知识组织 | 打开既有KB，不选文件，查看统一图、社区及跨文档实体路径；再进入来源过滤与问答 | 库级入口真实可用；共同实体身份唯一且可追溯，跨文档事实/证据关联成立，文件子图不是孤立的另一套知识 |

A16必须分项记录：A16-ENG为完整源码/依赖/模型与干净离线复建实装，A16-REL为真实目标发布及既定批准/签收。A16-ENG通过不能让A16整体或A16-REL变成PASS。其他用例如含工程与外部签收子项，也须逐项保留真实状态，不以汇总值隐藏未完成。

### 5.3 验收纪律

1. required用例为空、未跑、超时、SKIPPED或当前候选不匹配，均不能判PASS。
2. 每条记录case_id、输入版本、实际入口、预期、实际输出、结果、日志/trace和被测产物。
3. 局部模拟标SIMULATED，组件验证标COMPONENT，真实系统验证标INTEGRATION/UI；前两者不能充抵最终产品正例。
4. QA至少验证错值、错源、旧代、空结果和失去前提时确实失败。变异限于证明关键断言，不扩展成无尽框架工作。
5. 语义判断检查命题、限定和全部前提，不只匹配关键词、引用数量、URL格式或社区标记。
6. 同一事实的叙述措辞可以变化；不能用逐字一致替代内容正确，也不能用“模型随机”豁免错值。
7. 权限非干扰重点检查进入LLM的受控上下文与可见信号；输出措辞可有随机性，不能将此冒称基础模型训练数据隐私证明。
8. 模型/数据/实现/配置改变按依赖失效相关结果。新增日志不应使全部功能证据作废；不新建摘要/签名平台。
   应受控的实现不能移入排除目录以保住证据；必需用例不能通过改为optional、skip或移出收集范围取得通过。
9. 历史已修项要在当前候选复验；后续修复不得破坏已通过项。
10. 发现评审误报，记录当前源码、反例与推翻依据，由QA复核；单次未复现不等于已推翻。

### 5.4 A17的具体检查：证明“分散文档变成关联知识”

在同一知识库上传3份相关文档，分别给出：

- 文档甲：产品“星航贷”的AAA档定价为加30BP。
- 文档乙：客户甲的完整名称/简称、AAA评级、明确申请星航贷。
- 文档丙：星航贷信用方式分项上限1000万元。

以上仅作合成工程夹具，沿用其他验收的权限、版本和证据规则。

必须逐项验证：

1. 不选单文件，直接从“图谱增强”进入知识库级概览和统一图，范围和已发布代次明确。
2. 3份文档中的同一产品使用同域同代的canonical身份，围绕该节点同时存在来自各文档的真实事实，不能只是3张孤立图放在同一画布。
3. 从客户甲可沿真实“申请产品”关系找到星航贷，再查看AAA档加点及信用分项上限，并分别回到甲/乙/丙的原文支持。
4. 切换文件来源时，仅过滤/高亮对应证据或来源子图，canonical身份与代次保持一致；恢复库级视图后关联仍在。
5. 主题社区视图展示真实算法结果、层级、报告和支持来源；不得直接把每份文件包装成一个社区。无需强制所有社区都跨文档，也不能仅因社区数恰好等于文件数就判错。
6. 通过真实问答入口问“客户甲申请该产品，AAA档加点和信用方式上限分别是什么”，答案、适用条件及全部前提证据一致。记录实际local/global路径与消费的发布产物。
7. 更新文档丙并发布新代，库级图、报告、问答和引用同步切到新事实；删除/撤权依原规则生效，旧来源不得冒充当前。
8. 再加入确实无关联的合法资料，允许形成独立连通分量；系统不编造关系来达成“全库相互连接”。
9. 数据较大时验证有界展示，明确“完整索引范围”和“当前显示范围”。不能把显示节点上限当索引覆盖上限，不能以全库统计数字代替跨文档关系实证。

L2先完成图谱/来源相关子项；L3完成社区问答及逐结论证据，全项通过才将A17判PASS。纳入同一R15任务队列和最终必选集合，恢复后仍须检查。

## 6. 长程执行规则：每一种状态都有动作

复用现有任务台账；不足时仅维护以下4份轻量入口。文件名可映射至已有等价位置，首次写清实际路径，此后保持稳定：

- docs/r15/TASK.md：本任务书全文。
- docs/r15/TASKS.yaml：待办、依赖、所有权、下一动作和验收关联。
- docs/r15/NEXT.md：最新检查点和下一条精确动作。
- docs/r15/RESULTS.json：指向真实验收结果及当前候选，不以勾选替代测试。

原始证据放既有证据目录；迁移/备份/模型作业使用现有记录。技术裁决追加既有日志。

每项任务至少有：

id / parent_F_or_C / loop / owner / depends_on / state / next_action / acceptance_ids / evidence / blocker / affected_artifacts

### 6.1 完成的定义

代码写完 → 待验证；角色返回 → 待TL验收；测试通过 → 仅对所测候选和范围有效；真实用户旅程通过 → 对应产品能力已验证。

只有“实现、必需迁移/部署、正反例、消费者集成及TL验收”都满足，任务才VERIFIED。不能用PR合并、目录存在、HTTP200、成功状态或Goal achieved代替。

### 6.2 未完成时的动作表

| 现状 | 立即动作 |
|---|---|
| 一项完成 | 验证、集成、更新结果，立即派发下一项前置满足任务 |
| 子代理返回代码但无有效验证 | 退回具体失败判据或由QA复验；TL继续别的可执行项 |
| 测试失败 | 固定最小复现 → 定位生产者/消费者/数据/环境 → 修复 → 复验 |
| 同一路线三次无新证据/进展 | 换假设、缩小复现、调整方案或角色；次数不是停止目标的理由 |
| 缺可合法取得的依赖/模型/配置 | 创建获取/构建任务，使用授权源准备；其他工作继续 |
| 一项需要外部决策 | 写清准确问题、选择、影响和已准备结果，只暂停依赖该决定的动作 |
| 长任务正常运行 | 保存job/PID及监控方法，推进无冲突工作；不可重复启动或误判完成 |
| 准备工作过多但业务路径无进展 | TL收缩文档/通用化工作，亲自推进最短用户旅程至真实输出 |
| 验收证据因修复失效 | 重新执行受影响验证；不恢复旧bug以保住通过状态 |
| 用户要求进度 | 简报实际成果/失败/下一动作，随后继续；除非用户明确暂停 |
| 全部剩余工作确需外部权限/输入 | 完成所有准备、列明恢复条件，进入真实暂停；仍为未完成 |
| 执行器认证/额度/宿主不可用 | 保存检查点，进入PAUSED_RUNTIME；不改权限或无限重试绕过 |

### 6.3 每次Loop的收尾必须包含后续

- 已验证了哪个用户结果。
- 哪些任务重开/未完成。
- 下一任务、执行者、精确动作与检查条件。
- 若正在运行长作业，标出实际job与监控方式。
- 然后继续执行。

不以“下轮再做”“要不要继续”“建议优先做某项”结束仍有可执行任务的回合。

### 6.4 控制无效忙碌

队列选择按：交付阻断 → 用户完整路径 → 数据/安全正确性 → 发布阻断 → 一般改进。

不以文件、提交、台账条数表示进度。并列报告：F问题真实关闭数、A用例通过/未跑/失败、C能力已验证/待验、发布实际状态。

机制准备应尽快进入可用状态，随后回到业务开发；不将“不停机执行机制”扩建为新项目。

## 7. 会话持续、退出检查和宿主恢复

提示词定义行为；原生Goal/Stop机制驱动回合继续；持久检查点和宿主接续处理进程退出。三者要实际建立对应关系。

### 7.1 首先探测并启用

1. 读取实际宿主版本、帮助、会话ID和可用能力。优先启用CodeBuddy原生/goal，并查看状态确认ACTIVE。
2. 不把在聊天或shell里打印/goal当注册成功。
3. 当前IDE不能直接启用时，使用其实际支持的Goal/Stop能力，或受控CLI接管。版本不支持则选已验证替代；业务开发同步推进。
4. 使用prompt Stop hook时核实continueOnBlock=true实际生效。会话续跑采用一个主机制，避免多个调度者相互重启。
5. Goal评估依赖对话内容，并非独立读盘/跑测试；每阶段输出真实判据和结果，最终仍须执行产品验收。
6. 对评估器“达成/不可达”与实际任务、结果矛盾的情况，先核实真实输入、权限和剩余可执行项，再按真实状态继续或暂停。
7. 现有后台机制可用就复用。缺失时只补一个小型恢复入口和必要退出检查，不造通用代理平台。

### 7.2 待建立的两个项目入口

以下是本轮要求TL建立或映射的入口，并非声称仓库已经存在：

- bash platform/r15/bin/acceptance.sh --profile release  
  聚合真实必选验收并输出结构化结果。开发时可运行受影响子集。
- bash platform/r15/bin/resume.sh  
  核对任务、会话/进程和检查点，恢复指定会话；旧会话不可恢复时，新会话读取同一任务书和检查点接续。

优先包裹已有脚本。退出检查重用已验证结果并校验当前相关输入，不在每次Stop重跑完整验收。

项目包装器的退出码、状态、结果路径写清；不能把框架局部exit0当产品release通过。结果检查必须验证required用例集合完整、状态、证据存在和候选匹配。

### 7.3 退出决策

| 决策 | 条件 | 动作 |
|---|---|---|
| CONTINUE | 有可执行、可修复或可取得依赖的任务 | 返回精确next_action，同会话继续或由宿主接续 |
| RUNNING_JOB | 有真实存活、进展合理的作业 | 监控，继续无冲突工作，不重复创建 |
| DELIVERY_VERIFIED | F/A/C及工程交付条件全部满足 | 输出实际结果；若发布尚待真实外部条件，单列发布状态 |
| RELEASED_VERIFIED | 已完成既有授权目标发布、验证及所需真实批准 | 完成交付并正常收尾 |
| PAUSED_EXTERNAL | 所有剩余事项均确需不可自主取得的外部输入，且无可推进项 | 保存未完成项、待决动作、恢复条件；不能称全部完成 |
| PAUSED_RUNTIME | 执行器、认证、额度或宿主硬限制 | 保存状态，避免重启风暴，等待合法恢复 |
| PAUSED_USER | 用户明确暂停/停止 | 立即停止自动接续；只有新授权才恢复 |

DELIVERY_VERIFIED不是未经验证的“完成声明”，其完整条件见第9节。发布未完成时，不能以它清空本轮尚可执行的发布任务。

DELIVERY_VERIFIED是里程碑。退出检查遇到该里程碑后仍须检查发布队列：可执行则CONTINUE，确实全被外部条件阻塞才PAUSED_EXTERNAL。尚有正常长观察任务则RUNNING_JOB，不能提前完成。

长观察期间采用现有调度按有意义间隔检查，其他开发照常推进；全部只剩观察时，须验证下一次检查与接续会实际触发，再让当前计算回合等待。不能每轮高频重复相同状态命令，也不能取消监控后声称“后台会完成”。

Goal/Stop退出检查异常、状态文件缺失、证据损坏均不得当完成；诊断并修复机制或真实记录运行阻塞。

### 7.4 进程退出后的接续

1. 宿主恢复入口必须能实际调用执行者，而不仅仅启动一个daemon。
2. 记录真实repo/worktree、分支/HEAD、session_id、运行账号、恢复命令、日志、长作业ID和状态。
3. 恢复使用指定session_id，不能盲目继续“最近一次会话”。
4. 正常执行器仍存活时不启动第二个TL；新接续者检查单写入锁/进程身份后退出或附着。
5. 不能因短暂无输出/检查点旧就杀死作业。先检查PID、启动时间、命令、进展及资源；超预算才按项目范围处理。
6. 崩溃后先识别已有成功迁移、上传、发布、有效作业，再恢复；不重复副作用。
7. 前台转后台先写检查点、交接单写入权，验证新执行者已接管再退出。
8. 原生Goal能续回合不代表整机重启后自动恢复。仅在本来授权的托管范围验证重启恢复；共享宿主不擅自重启。
9. 宿主支持自动恢复时在项目范围启用；确实不支持时保留已验证的一条命令接续入口，准确说明实际恢复能力，不能宣称已自动恢复。
10. 认证失败、预算拒绝或用户暂停不可用无限重启绕过。相同致命启动错误触发退避诊断，不做无限空转。

官方CLI可按ID恢复会话；最终生成的包装器须按安装版本实测，不照抄未经验证的参数。

### 7.5 先做小范围恢复验证

在隔离测试会话/目录验证：

- 留一个必选任务未完并结束回合，机制应继续选择下一动作。
- 把任务勾完成但不给有效结果，应拒绝判完成。
- 模拟该测试执行器意外退出，恢复后仍到正确目录/会话，且只出现一个TL。
- 正常长作业短暂无输出，不被重复启动或误杀。
- 用户暂停后自动接续停止。

不杀实际生产任务来证明机制。验证够用即返回产品开发，现有机制已证明有效的部分直接复用。

## 9. 完成、发布与暂停的判据

### 9.1 工程交付完成：DELIVERY_VERIFIED

以下全部满足：

1. F01–F13均有修复后的验证，或有QA认可的明确推翻依据；没有OPEN、仅计划或SIMULATED充抵。
2. A01–A15、A17的全部工程必选子项及A16-ENG实际执行通过，required集合未缩减；确需真实外部批准的子项及A16-REL单列，不能将其伪装为已执行。
3. C01–C20及原有效必选扩展的工程实现和验证已完成；受影响部分复验，工程缺项关闭。目标发布和真实业务签收继续逐项记录，未满足时不能宣布C01–C20全部最终验收通过。
4. 用户页面实际完成多文档→知识库统一图谱→主题社区→global/local→原文证据，A17确认用户不必选择单文件也可查看跨文档知识结构；变更/删除/撤权/重启后成立。
5. 类型、代次、授权、原文证据和状态契约进入生产路径；无手工脚本旁路补齐。
6. 完整源码、离线依赖/真实模型及候选包可干净复建实装；恢复/升级/回退和既定容量、持续运行要求有真实结果。

### 9.2 最终发布完成：RELEASED_VERIFIED

- 实际明确授权的目标部署已完成，验证的是同一候选制品。

### 9.3 暂停条件

用户明确暂停；执行器真实不可用；或所有剩余工作确需不可自主获得的外部输入且无可推进项，才允许暂停。

暂停必须交付：

准确未完成项 → 阻塞证据 → 责任/资源 → 已准备结果 → 唯一必要决定或输入 → 恢复条件 → 下一精确动作 → 接续入口。

暂停不算完成，不使用“基本完成，只剩……”掩盖未满足的最终目标。
