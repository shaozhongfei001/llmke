# 差分升级的回滚：快照 + 按版本装回（2026-11-01）

上一轮把"能升级"做通了，但**能升不能退**——这种能力运维不敢用。这轮补回滚，
并把"回滚"里最容易做错的地方（自动卸载）明确排除。

## 做法：快照只存版本，不复制环境

`v2_delta_upgrade.py --snapshot <path>` 在升级前写：

```json
{"schema": "llmke.env-snapshot.v1", "python": "...", "at": "...",
 "packages": {"fastapi": "0.109.1", "pandas": "2.0.3", ...}}
```

为什么不复制 venv：几百 MB 到几 GB，而且 venv 里写死绝对路径，搬走未必能用。
**版本清单 + 离线 wheelhouse** 足以精确重建。

回滚 `--rollback <snapshot>`：

1. 读快照与当前 `pip list`，算出需要装回的 `name==version`；
2. `--no-index --find-links` 装回（离线）；
3. **不卸载**快照里没有的包，只列进 `extras` 交人决定；
4. 复核 `matches_snapshot`（只比快照里那些包的版本）。

## 为什么不自动卸载 extras

自动卸载是把"回滚"变成"再炸一次"的典型做法：新装的包可能被别的包依赖，
卸掉它会让原本正常的组件起不来。所以快照里没有的包只报告，不擅自删。
代价是回滚后环境不是"精确等于升级前"，而是"版本都对、多了几个包"——这个取舍写在报告里。

## 真跑（独立 venv，parse 基线 → 升级 → 回滚）

```
基线：numpy 1.26.4 / pandas 2.0.3 / fastapi 0.109.1
升级：装 81 个 wheel（新增 56 + 替换 25），repin numpy==1.26.4
      → pandas 2.3.2 / fastapi 0.162.0 / torch 2.6.0+cpu
回滚：restore 26 个包，extras 55 个（仅报告），matches_snapshot=true
      → pandas 2.0.3 / fastapi 0.109.1 / numpy 1.26.4，playbook 里三个包仍可 import
```

注意 `pydantic`：基线是 **2.14.1**，升级被降成 2.10.6，回滚又回到 2.14.1。
这说明"升级"并不总是升——清单里的版本可能比基线低，回滚必须按快照版本走，
不能假设"升上去的再降回来"。

## 还没做

- **没验服务进程**：只验 venv 里的版本与 import，没验服务用回滚后的依赖真的跑起来；
- **extras 未处理**：55 个多出来的包留在环境里，是否需要清理需要按依赖树判断；
- **没有"回滚失败"演练**：例如 wheelhouse 里缺少某个旧版本时该怎么办（当前会 FAIL 并列出）；
- 快照不含**系统级依赖**（apt 包、CUDA 驱动）与应用配置，那些不在 venv 里；
- 回滚不是原子的：装到一半失败会留下混合状态，需要重新跑一次（幂等，但窗口不干净）。
