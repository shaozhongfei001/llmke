# Fencing token：让旧主的晚到写入被拒（2026-10-31）

`lease.py` 增单调 fencing 计数、`rebuild.py` 增写入前校验，测试 6+10 项，双进程演练验证。

## 为什么 TTL 不够

上一轮的文件租约解决了"并发构建"，但留了一个窗口：
旧主从**实际失去租约**到**发现自己失去**之间（续租间隔内）仍可能写完指针，
把新主刚写好的快照指针覆盖掉。

TTL 调长只是把窗口变长或变短，**不能消除**。正解是 fencing：每次真正抢到租约都拿一个
单调递增的编号，写指针时校验"我的编号不小于当前指针的编号"。

## 三个实现要点

1. **计数器独立于锁目录**（`<path>.fencing`）：锁目录在释放/接管时会被删除，
   计数若放在里面就会清零、fencing 回退，旧主反而"合法"了；
2. **每次真正抢到才递增**，续租不变（同一主的重试 fencing 相同，允许覆盖自己）；
3. **校验在写指针之前**：落后就打掉刚建好的临时快照目录并抛 `StaleFencingError`，
   不给"先写后报错"留半成品。

## 实测

单进程语义（测试）：

```
fencing 递增：1 → 2 → 3（跨 acquire/release 也不回退）
旧主 fencing=1 写、当前指针 fencing=2 → StaleFencingError，指针未变
fencing 相同（同一主重试）→ 允许写入
```

双进程演练（B 先启动，A 6 秒后启动）：

```
B: builds=1, fencing=1, stale_write_blocked=True, not_leader=0
A: builds=0, skipped_fresh=1, fencing=2, stale_write_blocked=True, not_leader=220
```

- 合计 1 次构建；
- 两个实例各做了一次"用落后 fencing 写入"的模拟，**都被拒**；
- A 拿到租约后因快照指纹已新而跳过重建。

## 还没做（边界）

- fencing 计数器是**单文件**：多机共享存储上并发 acquire 仍依赖 mkdir 原子性，
  计数器文件本身的写入没加锁（靠"只有主会写"这个前提）——如果出现双主，
  两个主可能各写一次计数器，值仍单调但可能跳号；
- 没有把 fencing 暴露到读路径（读者只校验代次，不校验 fencing）；
- 未接外部存储（MySQL/Redis）的 fencing 实现；
- 演练里"旧主晚到"是**模拟**的（用 cur-1 直接调用），不是真实抢占时序；
  真实场景需要网络分区注入才能复现。
