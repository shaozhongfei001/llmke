# 多实例协调：重建租约（2026-10-31）

`graph_engine_adapter/lease.py`（6 项测试，含并发抢锁）、`rebuild_if_stale()`、
`scripts/v2_lease_drill.py`（双进程真跑）。

## 为什么需要

两个副本各自调度 → 各自全量重建 → 算力翻倍，还会互相覆盖快照。这是"重建能上生产"的最后一道门槛。

## 三个设计决定，每一个都是被现场打回来才定下的

**1. 用目录做锁本体，不是"读文件再写文件"。**
第一版是"读 meta → 判断过期 → 写 meta"。两个进程同时读到"没有租约"就双双写入、双双认为自己是主——
实测真的出现了两次构建。`os.mkdir` 是原子的，所以锁目录 = 原子占位，元数据放目录内的 `meta.json`。
并发抢锁测试（5 个进程同时抢）现在稳定只有一个赢家。

**2. 抢占后留 `claim_grace`。**
目录建好到写 meta 之间有极短窗口。别的实例此时读到"目录在、meta 没有"，如果按"过期"处理就会
把刚抢到的锁删掉（实测报 `FileNotFoundError: ... -> meta.json`）。所以 meta 缺失且目录年龄 < 3s
时按"别人正在抢"处理，直接让位。

**3. 长构建必须续租（`lease_guard`）。**
重建可能超过 TTL。不续租时租约会在构建中途过期，另一个实例"合法地"接管并同时构建——
这又是一次双主。加了后台续租线程后消失。
**踩到的坑**：第一版 `with lease_guard(...)` 只包住了 `time.sleep`，真正的构建落在块外，
等于没续租。改成包住整段构建才生效。

## 双进程真跑结果

```
B（先启动）：builds=1, not_leader=0, skipped_fresh=0     ← 主，构建一次
A（6 秒后） ：builds=0, not_leader=200, skipped_fresh=1   ← 全程被挡；拿到租约时快照已新，跳过
合计构建次数 = 1
```

第二行很关键：A 不是"没请求"，它请求了、也被调度了 200 次；拿到租约后发现快照指纹已覆盖当前文档，
于是**跳过重建**。所以既要租约（不并发），也要 `rebuild_if_stale`（不重复劳动）。

## Q 的变化

新增 `graph:多实例租约`：先起 B 再起 A（确定性顺序），断言合计只构建 1 次。
Q 现 **35 PASS / 0 FAIL / 0 NOT_IMPLEMENTED**。

## 边界（别当成分布式锁）

- 这是**文件租约**：单机多进程与共享存储（NFS/EFS）可用；跨机非共享盘不成立；
- 依赖文件系统时钟与 mtime，NFS 延迟可能造成短暂双主——所以**重建本身仍然幂等**
  （快照目录唯一 + 指针原子切换），租约只减少浪费，不是正确性的唯一保证；
- 没有 fencing token：被接管的旧主如果在"失去租约到发现自己失去"之间写了一次指针，
  仍然可能覆盖（当前只靠续租失败尽快停手 + 幂等重建兜底）；
- 未接 MySQL/Redis 等外部租约实现；未做多实例指标与告警。
