# 撤权 fence：先挡读、再重建（2026-10-31）

模块 `graph_engine_adapter/fence.py`（6 项测试），已接入 `pipeline.retrieve` 与社区报告。

## 设计依据与顺序

设计 §5 原文："首版可通过新隔离快照全量重建支持文档删除；**在新索引完成前撤权 fence
必须先阻止旧索引读取**。"

顺序是硬要求：先挡读、再重建。反过来就会出现一个窗口，把已撤权内容返回给用户。

## 三件事，缺一不可

1. **`revoke()`**：文件立刻不可见，并推进"代次"（generation）；重复撤权幂等，不重复推进；
2. **`assert_index_fresh()`**：进入检索**前**校验索引代次；索引比 fence 旧（或未声明代次）
   直接抛 `StaleIndexError`，拒绝读取；
3. **`filter_hits()`**：检索结果回来**后**再按来源过滤——引擎不认识撤权，它照样可能返回旧内容；
   一个命中若还有未撤权来源则保留并裁掉撤权来源，全部撤权则丢弃并记原因 `ALL_SOURCES_REVOKED`。

**为什么不能只做第 3 条**：只过滤等于默认"引擎一定会把撤权内容吐出来让我们拦"。
一旦引擎加了缓存或换了返回格式，这个假设就不成立。所以代次校验必须在读之前。

## 实测（假 retriever 故意返回已撤权内容）

| 场景 | 结果 |
|---|---|
| 撤权 999 后检索 | `hit_count=0`，`dropped=[{sources:[999], reason: ALL_SOURCES_REVOKED}]` |
| 索引代次 0 < fence 代次 1 | 抛 `StaleIndexError`，不返回任何内容 |
| 索引未声明代次 | 同样拒绝（不当成"最新"处理） |
| 一命中含 333+999 两来源 | 保留命中，来源裁成只剩 333 |
| 未配 fence | 行为与以前完全一致（`fence.generation = None`） |

最后一条是防回归：加安全机制不能悄悄改默认语义。

## 与社区报告的关系

撤权后 `build_report` 的 `known_files` 用 `fence.live(...)` 收窄，被撤权文件的事实以
`SOURCE_NOT_VISIBLE` 排除；两边都撤权时报告状态变 `BLOCKED`——**不能出现"检索侧说撤权了、
报告里还留着"** 这种自相矛盾。

## Q 的变化

新增 `graph:撤权 fence`（含"引擎返回旧内容也被拦下"与"代次落后拒绝读"两条断言），
Q 现 **28 PASS / 0 FAIL / 0 NOT_IMPLEMENTED**。

## 还没做（不许当成删除已支持）

- **引擎侧按文档删除图产物**：未实现。`delete_document` 仍是 NOT_IMPLEMENTED；
- **隔离快照全量重建的编排**：未实现（只有 fence 与重建后的代次校验）；
- 撤权后的索引重建是**离线/后台**动作，没有调度与超时管理；
- 没有验证"重建过程中并发查询"的真实行为（当前只有代次校验这一层）。
