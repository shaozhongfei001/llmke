# 重建故障边界：背压、指数退避、告警（2026-10-31）

`graph_engine_adapter/rebuild_coordinator.py` 增三个开关（测试从 5 项加到 10 项）。

## 要解决的问题

模型/引擎一旦不可用，重建会连续失败。如果没有边界，会出现三种失控：

1. **队列无限增长**：每次上传都往积压里塞，最后吃内存；
2. **打爆下游**：`run_once()` 被反复调用，退避缺失时每次失败都立刻重试，把不可用的模型再压一遍；
3. **故障无声**：连续失败没有出口，只有翻日志才知道。

## 三条边界

| 开关 | 行为 |
|---|---|
| `max_pending` | 积压到上限时 `request()` 直接返回 `BACKPRESSURE` 并计数，**拒绝入队** |
| `backoff_base / factor / max` | 连续失败后指数退避（1s→2s→4s…封顶），退避期内 `run_once()` 返回 `BACKOFF`，不碰下游 |
| `alert_after` + `on_alert` | 连续失败到阈值回调一次告警；回调在**锁外**执行，避免与业务锁互等 |

另外：**成功即复位**（`consecutive_failures=0`、`next_attempt_at=0`）；
失败时整批请求放回队首，一条不丢。

## 实测（Q 内确定性检查，假时钟驱动）

```
rejected=BACKPRESSURE, delays=[1.0, 2.0, 4.0], alerts=1, pending_kept=2
```

- 第 3 条请求在积压满时被拒，不入队；
- 退避 1s → 2s → 4s（`backoff_max=4` 封顶），退避期内返回 `BACKOFF`；
- 连续失败到阈值时告警**只触发一次**（阈值那次），不是每次失败都喊；
- 队列里始终保留那 2 条请求，没有因为失败被丢掉。

## 还没做（别当成"故障处理已完成"）

- **真实告警通道**：`on_alert` 只是个回调，没有接监控/工单/消息；
- **定时调度**：没有"退避到点自动重试"的调度器，需要外部循环调用 `run_once()`；
- **多实例协调**：单进程语义，多副本会各自重建；
- **背压的上游表现**：`BACKPRESSURE` 目前只返回给调用方，上传接口还没有对应的用户可见提示；
- 退避参数没有按真实故障时长调过（本地演练都是毫秒级失败）。
