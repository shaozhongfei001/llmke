# 07 备份与灾难恢复设计

> 状态：**设计草案**（补齐原设计缺口）。
> 文中 RPO/RTO 与保留份数为**建议值**，需业务确认；不是实测结论。

## 1. 要保护什么

| 对象 | 位置 | 丢失后果 |
|---|---|---|
| 指针（当前发布版本） | `pointer.json` + MySQL 发布表 | 读者读到旧版本或读不到 |
| 图快照 | `snapshot-*/`（graph、openie、chunks） | 需全量重建，耗时且结果可能不同 |
| 元数据 | MySQL（文件版本、构建、发布、租约） | 无法判断哪份快照对应哪批文档 |
| 契约与配置 | `contracts/`、引擎配置 | 重建结果不可复现 |

## 2. 目标（建议值）

- **RPO ≤ 24h**：最多丢一天的新建/变更。
- **RTO ≤ 4h**：从发现损坏到恢复可读。
- 保留最近 **3 份**已发布快照，任意一份损坏可切到上一份。

## 3. 设计

### 3.1 快照不覆盖写

每次发布生成新目录，**从不原地修改**。旧快照在保留期内只读保留，删除由保留策略统一执行。

### 3.2 清单与校验

每个快照目录必须有 `manifest.json`：文件列表 + 大小 + sha256。
恢复前先校验清单，任一文件不匹配即中止，**不允许"部分恢复"**后切指针。

### 3.3 指针切换是唯一发布动作

恢复 = 校验通过后原子替换指针（CAS：旧值匹配才写入）。
指针写失败不影响旧版本可读。

### 3.4 异地副本

每日一次全量复制到独立介质（对象存储或另一台机器），与在线快照**不同故障域**。
只备份快照不够：MySQL 元数据必须同批次导出，否则恢复后无法对应文档。

## 4. 恢复流程

1. 选目标版本（最近可用快照 + 对应元数据导出）。
2. 校验 `manifest.json`（全量 sha256）。
3. 恢复元数据到隔离库，核对文档数/构建记录。
4. 校验图规模（节点/边/事实）与发布记录一致。
5. 原子切指针。
6. 冒烟：3 条固定查询的命中与恢复前一致。
7. 记录恢复事件（时间、版本、操作人、差异）。

任一步失败：**不切指针**，保留现场。

## 5. 演练

- 季度一次：从备份恢复到隔离目录，跑上述 1–6 步。
- 演练结果必须留证据（耗时、校验通过率、冒烟差异），否则视为未验证。

## 6. 未决

- 保留期与合规要求（是否 6 个月/1 年）。
- 是否需要对快照做增量备份（当前按全量复制设计）。
