# 08 容量与性能设计

> 状态：**设计草案**。目标值为**建议值**，需业务确认；当前实测样本很小（5–10 块），不可外推。

## 1. 目标（建议值）

| 指标 | 目标 | 说明 |
|---|---|---|
| 单库文档数 | 10 万 | 单客户部署，按最大客户估 |
| 单库文本块 | 500 万 | 平均每文档 50 块 |
| 图规模 | 2000 万节点 / 1 亿边 | 由块与三元组比例推算，需压测校准 |
| 检索延迟 P95 | ≤ 3 s | 不含答案生成 |
| 答案首字延迟 P95 | ≤ 5 s | 流式 |
| 单次全量构建 | 10 万块 ≤ 8 h | 离线窗口内完成 |
| 增量构建 | 变更 1% ≤ 30 min | 抽取只跑新块，图仍需重建 |

## 2. 瓶颈与顺序

1. **LLM 抽取**：每块一次调用，是构建主成本；可批处理与并发，受配额约束。
2. **图重建与 PPR**：当前增量是"增量抽取 + 全量重建图"，图越大重建越慢，是主要风险。
3. **向量检索**：随块数线性增长，需索引参数与分片策略。
4. **MySQL 租约/发布**：行级争用，非主要瓶颈。

## 3. 现有实测（小样本，仅作基线）

| 场景 | 块数 | 全量 | 增量 | 倍率 |
|---|---|---|---|---|
| 双快照对照 | 5 | 32.4 s | 7.5 s | 4.3× |
| 高相似压力语料 | 10 | 63.5 s | 7.3 s | 8.7× |

结论只能说明"增量路径有效"，**不能**用于推算 500 万块耗时。

## 4. 控制手段

- **配额与限流**：已有 `quota.py` / `rate_limit.py` / `backpressure.py`；积压满时拒绝并给用户可读提示。
- **批量抽取**：按 token 预算合并块，减少调用次数。
- **图分片**：按可见集合或文档域分片，避免单图无限增长（**未实现**）。
- **冷热分层**：旧版本快照转冷存储，只保留指针可达的版本。

## 5. 压测方法（必须补做）

1. 合成阶梯语料：1 千 / 1 万 / 10 万块，块间高相似（防"语料太容易"）。
2. 固定查询集 50 条，测 P50/P95 检索与答案延迟。
3. 记录构图时间、内存峰值、磁盘占用。
4. 增量场景：变更 1% / 10%，记录重建耗时。
5. 结果写入证据文档，未达标则回到设计调整。

## 6. 未决
