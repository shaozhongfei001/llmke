# 增量重建：复制快照 + 按文本差集删除/新增（2026-10-31）

之前每轮重建都从零跑：新建空目录 → 全量文本 → 每块都过一遍 LLM 抽取。
本轮把"复制上一份快照再就地改"打通，实测全量 32.4s → 增量 7.5s（4.3×）。

## 为什么要复制，而不是原地改

旧快照在切换前还要被读者按 fence 代次读。原地改等于**边读边写**：读者可能读到
删了一半的图，而这恰恰是隔离重建要避免的事。复制的代价是磁盘 IO，全量的代价是
**每块重新过 LLM**——差着数量级，所以复制是划算的。

失败语义与全量一致：apply 抛异常 → 删掉半成品目录、指针不动。

## 差异按"文本集合"算，不按 file_id

块的 id 就是文本哈希。撤权、改名、内容微调，在引擎眼里都是"这段文本没了、那段来了"。
按 file_id 做需要额外映射表，多一层就多一处会错。所以：

```
existing = 引擎里现有块文本集合
to_delete = existing - 新文本集合
to_add    = 新文本集合 - existing
```

顺带的后果（写清楚，免得被当成 bug）：**内容改了 = 删旧块 + 加新块**，不是原地更新。

## 到底"增量"在哪

| 环节 | 增量？ | 说明 |
|---|---|---|
| OpenIE 抽取 | **是** | `hp.index(to_add)` 会 `load_existing_openie()` 复用已有结果，只对新块调 LLM |
| 向量编码 | 是（按需） | 嵌入存储按文本哈希去重，旧块不重编码 |
| 图构建 | **否** | `add_fact_edges` 遍历所有块重建图 |
| 快照目录 | 复制 | 磁盘 IO 换掉 LLM 调用，仍然划算 |

所以准确说法是"**增量抽取 + 全量重建图**"。别把这两个说成一回事——本轮证据里
也是这么写的。

## 增量的 fencing 校验不能被绕

`_promote()` 把"校验 fencing → 写指针 → 清理旧快照"抽成公共段，全量与增量共用。
否则被接管的旧主可以走增量这条路绕开写入保护（这是新增路径最典型的漏点）。
测试 `test_delta_rejects_stale_fencing` 专门钉这一条。

## 真跑（5 块真实投影载荷，含 CJK 补丁）

```
全量：32.4s，5 块，openie 5 条
增量：7.5s，删 3 块（333）+ 增 1 块，复用 2 块，剩 3 块，consistent=True
openie：5 → 3，与期望 5-3+1=3 完全相等（等号不成立就说明存量被重跑）
被删文本：在快照里已不存在（deleted_still_present=[]）
指针：mode=DELTA、fencing=1、documents=3
```

"openie 条数必须等于期望值"是本轮最关键的断言：只看"增量跑完了"完全不够，
条数不对就说明有人偷偷重抽了存量。

## 拒绝执行的三种情况（都测了）

- 没有上一份快照 → `RebuildFailed`，**不偷偷降级成全量**（否则"增量"这名字就没意义）；
- 全部文件撤权 → 拒绝生成空快照；
- fencing 落后 → `StaleFencingError`，指针不动。

## 还没做 / 边界

- **检索质量未测**：只验了结构性一致（块数、openie 条数、被删文本消失），
  "增量后答得还准不准"需要重排模型，波动大，单独评估；
- **相同文本会合并**：两份文件内容若完全相同，块哈希相同会并成一块，
  `duplicates` 会记数但快照里只有一份（这是引擎语义，不是本轮引入）；
- **磁盘成本**：每次增量复制整个快照目录（含 igraph 与嵌入），大库需要配额/清理策略；
- 未接调度器：`rebuild_delta` 目前由脚本/调用方驱动，`RebuildCoordinator` 仍走全量；
- 未做能力声明（`describe()` 里还没登记 DELTA），下轮补。
