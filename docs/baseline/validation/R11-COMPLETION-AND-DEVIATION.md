## 5 偏离原因（按责任大小）

### 5.1 选错了优化目标（主因）

每轮都有两条路：
- A 做产品功能（解析/向量/模型）——依赖外部、反馈慢、可能失败；
- B 做门禁/证据/文档——立刻变绿、可断言、不会失败。

我持续选了 B。**证据**：R8 的 10,163 行验证文档 vs 980 行产品代码。

### 5.2 开工前没有做工作量估算

参考系统 116,216 行、575 端点、9 个 Java 模块。正确做法是第一轮就给出
"对齐需要多少人日 / 缺哪些依赖 / 建议先做哪 3 个能力"。实际是直接开了一个 Python 骨架。

### 5.3 把"骨架完成"误当成"系统完成"

6 个模块各自"完成"：能建块、能拼证据、能生成 SQL、能返回 JSON。
但拼起来**用户不能上传文档、不能语义检索、不能生成回答**。每块都绿，整体为零。

### 5.4 环境约束发现得太晚

PyPI 不可达、无 torch/transformers/pymilvus、无 ollama、无 LLM 端点——在第十轮末才系统检查。
这些应在第一天盘点，并据此调整目标（而不是先假设"能装"）。

### 5.5 元工作与产品工作混在一起统计

`framework-verify` 322 条通过、13 个批次、`digest_scheme=4`——这些都是真的，
但它们衡量的是"证据是否自洽"，不是"系统是否能干活的"。把两者混报，掩盖了产品为空。

## 8 结论与路线建议

**结论**：本系统不是"参考系统的 80%"，是"参考系统的骨架 + 一套超出参考的证据机制"。
产品侧完成度约 1.5%（行数）/ 0.3%（端点）。

**三条路线（需评审裁定）**

| 路线 | 做法 | 前提 | 风险 |
|---|---|---|---|
| A 复刻参考架构 | 引入 Java 9 模块 + Python 算法服务 | JDK/Maven/Milvus/ES | 依赖重，但可直接复用参考实现 |
| B Python 重写 | 以现有 6 模块扩成完整服务 | 可装包（当前不可） | 575 端点业务面重写，量大 |
| C 混合 | Java 网关 + Python 算法 | 同 A | 与参考同构，迁移成本最低 |

**当前硬约束（VERIFIED）**：PyPI 不可达；无 torch/transformers/pymilvus；无 ollama/LLM 端点。
在依赖放开前，任何"对齐参考"的计划都无法落地。
