# 外部评审说明（提交给独立 Agent）

你收到的是一份**自带数据、但不带仓库**的评审包。你的任务是判断三件事是否成立，
并给出可执行的路线建议。**不要为"做得辛苦"加分，也不要因"文档很多"给分。**

## 1. 材料清单

| 文件 | 用途 | 你该怎么用 |
|---|---|---|
| `01-COMPLETION-AND-DEVIATION.md` | 主报告：目标 vs 现状、工时分布、12 项能力矩阵、偏离归因 | 核对算术与逻辑，找出"结论强于证据"的地方 |
| `02-REFERENCE-ALIGNMENT.md` | 参考源码实测规模与能力清单 | 核对基准是否被夸大或缩小 |
| `03-FACTS.md` | 可复算事实：门禁结果、批次状态、测试数、schema 数字 | 当"事实底稿"，不要当结论 |
| `04-CODE-INVENTORY.csv` | 逐模块：文件数/实现行/函数数/测试用例 | 看投入结构，不看绝对值 |
| `05-ROUND-TIMELINE.csv` | 每轮按路径分类的新增行数 | 判断"工时是否错配" |
| `06-EVIDENCE-INDEX.md` | 证据文件索引与各自能证明什么 | 判断证据是否支撑结论 |
| `07-SOURCE-SAMPLES/` | 5 个代表性源文件（含 2 个测试） | 判断代码质量与"骨架"判断是否成立 |
| `08-OPEN-DECISIONS.md` | 三条候选路线与依赖约束 | 给出你的选择与理由 |

## 2. 你必须先接受的三个前提

1. **你无法运行代码**。所有数字都是"声称"，你的工作是检查**内部一致性**（算术、逻辑、结论与证据是否匹配），
   而不是验证真实性。
2. **"通过"指技术门禁**，不指业务可用；**独立 QA 从未签署**。
3. 参考系统只有静态源码，其能力清单由类名/端点/依赖**推断**，非运行实测。

## 3. 请回答的 10 个问题

**A 结论类**

1. 「完成度约 1.5%（按实现行）/ 0.3%（按端点）」这个算法是否合理？若不合理，你认为更合适的度量是什么？
2. 「本系统是骨架，不是参考系统的 80%」是否成立？请指出报告中支撑不足的句子编号。
3. 「偏离主因是把可验证当成有价值」是否成立？还是另有更主要原因（例如需求本身不可行）？

**B 归因类**

4. 工时分布显示「验证文档 10,562 行 : 产品代码 1,787 行」。这是"必要投入"还是"错配"？请给出判据。
5. 报告称环境约束（PyPI 不可达、无模型/中间件）是硬阻塞。你认为这个理由是否被用来掩盖执行问题？

**C 路线类**

6. 三条路线（A 复刻 Java / B Python 重写 / C 混合）你选哪条？给出前提与首三个里程碑。
7. 现有 1,781 行实现中，哪些应保留、哪些应丢弃？请按"迁移成本 vs 重写成本"给结论。
8. 若只能先做 3 个能力让"用户能上传文档并得到基于语义的回答"成立，选哪 3 个？

**D 风险类**

9. 继续在现有骨架上扩建的最大三个风险是什么？
10. 如果你是我的业主，你会立刻叫停什么？会立刻批准什么？

## 4. 输出格式（请严格按此输出）

```
【结论】完成度结论: 成立/不成立（理由 ≤3 条）
【算术】报告中算错的数字: <列表，无则写"未发现">
【夸大】结论强于证据的句子: <引用原文 + 为什么>
【归因】偏离主因: <你的判断，与报告一致/不一致的理由>
【路线】推荐: A/B/C + 三个里程碑 + 前提
【保留/丢弃】: <按模块列>
【三个能力】: <按优先级列>
【风险】: <三条>
【叫停/批准】: <各一条>
```

## 5. 禁止事项

- 不要因"文档多、测试多"推断质量高——报告本身承认这是错配。
- 不要假设参考系统可运行；也不要假设它不可用。
- 不要给出"继续努力"这类建议；只给可执行判断。
- 不要修改材料；只输出评审结论。
