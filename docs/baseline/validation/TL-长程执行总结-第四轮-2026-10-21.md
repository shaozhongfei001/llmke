## 3. 关键结论（四条）

### 3.1 QA 信任链是闭环的，卡的不是技术

- 信任根在工作区外，**不在** `FROZEN-MANIFEST` 内（实测 0 命中），`control_digest` 也只覆盖仓库内文件
  → **更新锚点不会改变候选，不存在循环**
- 比较是**单值相等**：`c8a73c37…`（旧）≠ `213c6ebc…`（r5）→ 任何签名都会被拒
- 签署窗口 1 小时，从 `issued_at` 起算；被签署的是 `subject_sha256`（**不含时间字段**），
  过期后重建**不改变被批准的内容**

**必须说清的局限**：框架只能拦「签署者出现在 `implementation_principals` 里」，
**拦不住「实现者拿别人的钥匙签」**。独立性只能靠钥匙与执行者分离。

### 3.2 P0-02 的方法论发现：计数一致 ≠ 语义对齐

`dialogue` 实体 13 字段 = 台账 13 字段，**计数完全一致**，但设计文档要求建 `user_id` 索引，
而实体里根本没有这一列（只有 `createBy`）。

→ 用「字段数对不对」验证表结构是**不充分**的，必须靠真实 DDL。

### 3.3 扫描范围不固定，是目前最隐蔽的可复算性缺陷

`security-check` 扫的是**整棵工作树**，每跑一次门禁就多一个 `evidence/*.log`：
502 → 503 → 507 → 514 → 517。

**本轮还因此踩了一次真实的坑**：`db-entity-check.json` 写入源码绝对路径，报 39 处
`PERSONAL_ABSOLUTE_PATH`——是我在 `a378c23` 引入、当时漏跑 `security-check` 才没发现。
已改为相对路径 + 生成器自检拒绝写入（`FAIL-4TH-01`）。

### 3.4 PDF：两臂都跑不起来，不能假装验证过

| 臂 | 状态 | 原因 |
|---|---|---|
| 旧解析臂 | NOT_RUNNABLE | 缺 `magic_pdf`/`onnxruntime`/`cv2`/`tika`/`fitz` |
| doc2md 臂 | NOT_RUNNABLE | 无 `.venv`，包不可导入 |

**没有静默切 `pdfplumber`**——那会得到「测试通过但能力缺失」的假象。
本轮只交付：就绪度证据（6 份样本 SHA256）+ 验证协议 + 输入清单。
