## A. 十条问题的处置

### 1. 关闭是否合规 → 接受
- 措辞按评审修正：本轮是**业主接受风险并关闭轮次**，不是"批次满足正常 QA 收口条件"。
- `CLOSED_WITHOUT_ENDORSEMENT` 不是门禁规范里的合法终态；规范只有
  `DONE / SUPERSEDED / RETIRED`。因此该状态**只作为账本备注**，未伪造为 `DONE`。
- 已确认：r10 的自签不称独立 QA；r11 仍 `QA_PENDING`；P0 全 OPEN、L1–L4 BLOCKED。
- 动作：`CLOSE.md` 增补"不等于通过 QA 收口"的显式句。

### 2. 不足证明"同一棵树" → 接受（关键缺口）
- 评审指出的补强实验，我确认**没做过**：
  ① 改一个"影响执行但不在门禁摘要依赖集"的文件，尝试复用旧证据；
  ② QA 执行后、`accept-qa` 前变更输入，再尝试接受旧结果。
- 我做的四组对抗只证明"已纳入摘要的改动会触发失效"，**不证明摘要无漏项**，也不覆盖检查—接受之间的竞态。
- 现状：没有 commit/tree SHA、干净状态、输入清单、环境摘要的绑定；外部 QA 的复跑结论仍是**未签署的复核记录**。
- 结论：这是本轮最实质的缺口，列入下一轮第一优先，不在本轮补（改控制面会使 r11 失效，而 r11 已无签名路径）。

### 3. control_digest 过粗 → 部分接受（建议对，代价未消失）
- 接受问题本身：把全部 `loops/*/LOOP.yaml` 纳入一个摘要，使"新建无关批次"作废旧批次，属**不必要的耦合**。
  我此前把它写成"既定代价"，是**把设计缺陷合理化了**。
- 接受拆分方向：基线控制摘要 / 每批次 gate-spec 摘要 / 每门禁测试与依赖摘要。
- 保留意见：拆分需要改 `controls()` 与 `FROZEN-MANIFEST` 结构，属控制面变更，须在下一窗口一次做完，
  且需处理旧批次记录的兼容（scheme 升级 + 不回溯改写）。

### 4. 窄 code_digest 会留假绿 → 接受
- 风险清单（漏列目录、动态导入、配置/模板/schema、生成代码、构建脚本、依赖锁、非 `.py` 测试、
  未跟踪文件/符号链接）我确认**当前实现均未覆盖**。
- 特别承认：`code_digest` 覆盖率**从未独立验证**，不能当完整性事实引用。
- 接受兜底策略：门禁每次运行生成**实际输入清单**并绑定其哈希；依赖闭包无法确定的门禁，
  回退到更宽摘要；"依赖未声明但 PASS"默认拒绝。

### 5. 作废六次 → 部分接受（含我方计数错误）
- **计数错误（评审指出）**：`SUPERSEDED` 共 6 个（r3、r5、r6、r7、r8、r9），其中
  **本轮内作废的是 5 个（r5–r9）**，r3 属历史遗留。原文"作废六次"混淆了两种口径，已更正。
- 分类同意：r6（冻结时序）、r8（漏授权条目）属**可提前避免的完整性检查缺失**；
  r7 属范围变更（业主弃用）；r5 属正常迭代。
- **r9 → r10 的替代原因：记录缺失**。决策记录中没有条目说明，仅有提交信息。
  我不推断原因，据实标为"未记录"，这是流程缺陷而非表述问题。
- r10 的 `DONE` 与"九条全 STALE"必须分列（见 B-3），原文合并表述会造成误读。

### 6. r2/r4 孤儿批次 → 接受
- 处置：保留全部证据与日志，**不改旧文件内容**，仅通过受控状态迁移追加剧终态与原因。
- 已执行（见 B-4）：`r2: QA_PENDING → SUPERSEDED`、`r4: IN_DEV → SUPERSEDED`，
  记录裁决主体（TL 归档，业主可否决）与替代批次。
- 说明：`r4` 如仍有有效工作，恢复需重新建批而非"复活"旧状态。

### 7. 回执放进 control_digest 不合理 → 接受（我原方案有循环）
- 评审指出：`control_digest` 表达控制规则，不应含运行后产生的接受凭证，否则 accept 写回执
  会改变自身依赖的摘要，可能循环或使签名后摘要变化。**这一点我原方案没有考虑，属设计错误。**
- 修正后的设计：回执归入**该批次证据**（记录被接受的 subject、信封哈希、验证器版本、结果、
  接受时间），由证据清单绑定；若需证明"确在有效期内接受"，必须有**受信时间戳或受保护的
  追加式审计记录**，无法提供时标"接受时点未证实"，不得用回执文案补足。
- 动作：`BL-1.1.1-01` 的 proposal 需按此改写——该文件在控制面，**留待下一窗口**，
  本轮仅在决策记录中标注"原 proposal 已被评审否定，不得照原样实施"。

### 8. 是否改"长有效期 + 一次性消费" → 不接受（但接受其语义拆分）
- 不建议改长有效期：扩大重放窗口；且"一次性消费"需要可靠原子存储，仍证明不了历史接受时间。
- 但接受评审给出的语义拆分，并认为这才是正确方向：
  **接受时**严格检查短有效期；**历史复核时**只验证签名、subject、签署者授权与撤销状态，
  不因载荷过期而否认过去的接受；接受时间由受信回执证明，无回执则标注未证实。
- 这正是 W-07 想解决而做错了的问题：W-07 错在把锚点放在未签名可变状态（`STATE.json`/`ran_at`），
  不是错在"历史复核不应被时间否证"这个目标。

### 9. 同机同用户不同密钥是否独立 → 接受（与我此前结论一致）
- 不构成充分独立。`implementation_principals` 只比对主体名，拦不住"同一双手换身份"。
- 采纳最小标准：QA 由有权主体指定；实现者无权读取 QA 私钥；QA 操作者不负责被审实现；
  QA 在受控身份/环境独立拉取指定 commit 并复跑；签名绑定运行结果与输入哈希。
- 同主机可行，但必须有真实账号、ACL、密钥保管隔离；否则只能记"风险接受"，不得记"独立背书"。

### 10. 只能改一处 → 接受
- 采纳：**独立签名执行证明**——由独立身份在受控 runner 上，对
  `commit/tree SHA + 干净状态 + 门禁定义 + 依赖输入清单 + 执行环境 + 日志摘要` 一次性签名，
  接受与复核都验证这份证明。
- 理由同意：它同时回答"谁跑的、跑了什么、签的哪棵树"，比继续堆松散摘要更能提升可信度。
- 边界同意：仍不替代 P0 所需业务输入与真实环境测试。
