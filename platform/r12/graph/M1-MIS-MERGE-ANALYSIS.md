## 1. 先说结论：不是 canonical 归一规则在把概念并成数值

归一链路只有三处（`graph_types.py`），全部可读可复核：

| 环节 | 代码 | 会不会把「授信额度」并成「5000万元」 |
|---|---|---|
| 停用词过滤 | `STOPWORDS`（下表/天数/业务日/客户/产品…） | 不会。两个词都不在表里 |
| 合法性过滤 | `is_valid_entity()`：纯数字、文档标题、夹具词、长度 2–30 | 不会。`授信额度` 合法保留；`5000万元` 因为命中 `RULE_AMOUNT` 也被**故意保留** |
| canonical 归一 | `canonical_of()`：①别名表 ②`名称是另一实体的严格前缀` 且后者带公司/机构后缀 | 不会。`5000万元` 不是 `授信额度` 的前缀，也不带公司后缀 |

另外 `data/alias_map.json` 在本环境**不存在**（`load_alias_map()` 返回空表），所以也没有"手写别名把概念指到数值"。

→ 真正的成因是**LLM 抽取阶段**：模型把"授信额度是 5000万元"里的**取值**抽成实体，**概念**要么没抽、要么抽成一个孤立节点，导致：

1. **概念-数值关系化**：图里是 `智造贷 -单户最高授信额度-> 人民币5000万元`，`授信额度` 这个节点**与 `智造贷` 没有边**；
2. **数值实体分裂**：同一数值多种写法各成一个节点；
3. **单位/泛词入图**：`万元`、`额度` 这种根本不该是实体的词成了节点。

第 1 条正是"概念被数值替代"的观感来源，也是 local 检索"问授信额度查不到图"的直接原因（实体链接锚点缺边）。

## 3. 建议的判定规则（4 条，前 3 条确定性、可单测；第 4 条需你确认是否入核心）

**R1（单位/泛词黑名单，最小改动）**
把下列词加入 `STOPWORDS`：`万元 / 亿元 / 元 / 个基点 / 基点 / BP / 额度 / 额度上限 / 天数 / 业务日`（后两者已在）。
判定式：`clean_name(name) in STOPWORDS → 过滤，reason="unit_or_generic"`。
影响面：只删节点，不动边语义（`智造贷 -最高额度-> 5000万元` 仍成立）。

**R2（数值写法归一，确定性）**
对命中 `RULE_AMOUNT` 的名字做规范形：去 `人民币` 前缀、去 `加/减` 动词、去空格 → `5000万元`、`1000万元`、`30个基点`。
判定式：`NUMERIC_CANON = re.sub(r'^(人民币|加|减)', '', s)`，归一把 `人民币5000万元→5000万元`、`加30个基点→30个基点`。
**必须**同时写 `merged` 映射（现状 `normalize_graph_data` 已有 `merged` 字段，天然可审计）。
风险：`信用部分不超过1000万元` 不能这样归一（它带语义限定），建议**不参与 R2**，交给 R3。

**R3（概念-数值：禁止合并，改为补一条正/反向边 + 保留 mention）**
判定式（三条同时成立才允许建立 `概念 -取值-> 数值`）：
1. 概念名命中 `RULE_INDICATOR`（现有 `RULES` 里 `(率|占比|额度|余额|存款|用电量|…)$`）；
2. 数值名命中 `RULE_AMOUNT`；
3. 二者在**同一个 chunk**（`chunk_pk_list` 有交集）内共现，且该 chunk 文本里存在 `<概念>…<数值>` 的相邻共现（中间 ≤ 8 个字符）。
产物：`概念 -取值-> 数值`（orientation=确定性，不用 LLM）。**绝不改概念名**，因此不会出现"问授信额度、答的是数值节点"的情况。

**R4（原始 mention 与证据，审计/回滚）**
顶点属性增加：
```json
"mentions": [{"text": "授信额度", "chunk_pk": "...", "file_id": "...", "offset": [0, 459]}],
"norm_rule": "R2",          // 被哪条规则改过
"norm_from": "人民币5000万元"
```
判定式：任何 R1/R2/R3 的动作都必须写 `norm_rule`；没写的节点视为"未经归一"，可整链回滚（按 `norm_rule` 反查）。

**明确不做的**（避免把"未分类强塞类型只为让计数归零"）：
- 不把概念节点并进数值节点（禁止 `授信额度 → 5000万元`）；
- 不用相似度/模型做实体归并（不可复现）；
- 不改 `ALLOWED_TYPES` 白名单去凑类型覆盖率。

### 9.2 为什么（不是 migrate 写错，是顺序缺一步）

TL 定的重建顺序是 `del_space → 重抽 → 重建社区`；本次实际是 **`重抽 → 重建社区`（追加）**。
没有 `del_space`，所以：
- 新代实体写进去（同名 vid 按名字覆盖/新增）；
- 旧代顶点一个没删 → 55 个仍带旧 file_id；
- 归一化只在"写入时按名字归并"的程度上发生，**合并源不会被删除**，于是源与目标共存。

每重抽一次就叠一层代次；今天只多 4 个看不出，多跑几轮就是"同一实体 N 份、N 个 file_id"。

### 9.3 引用可回指的三层真实状态（**措辞更正**）

```

                                                 状态：**新代**（实测 2/2、100%）
文件级（community.sources / global 引用卡片 / Java getByIds）
                                              -> Nebula 顶点与边的 file_id
                                                 状态：**仍是旧代 258/266/268**
顶点级 file_id 被当成 chunk pk 用的路径        -> 全仓不存在（pk 只有 Milvus 一处产生）
```
调用链（逐行核过）：

### 9.4 命名坑（别当成 chunk_refs 悬空的根因）

### 9.6 边级代次（比顶点更严重，直接放大文件级引用问题）

### 9.7 读法不对称（会把"属性没落库"误判成事实，务必记住方向）

同一 space、同一份数据，顶点与边的属性访问**规律相反**（已实测）：

```
顶点：RETURN v.name              -> NULL        RETURN v.entity.name -> 有值     FETCH PROP ON entity -> 有值
边  ：RETURN e.name              -> 有值        RETURN e.relationship.name -> NULL    properties(e) -> 有值
```
所以纪律不能写成"一律带 tag 前缀"：
```
顶点 -> 必须 v.<tag>.<prop> 或 FETCH PROP
边   -> 直接 e.<prop> 或 properties(e)；**不要** e.relationship.<prop>
```
后人为了"统一风格"把边改成 `e.relationship.x` 会得到成片 NULL，并再次误判"写入没生效"。

### 9.8 根因定案：`del_space` 静默空转（"重建"退化成"追加"的直接原因）

实测（一次性探针空间，未触碰 `g_kb_9`）：

```

   SHOW SPACES 中**仍然存在**          <- 零删除，但返回成功
POST 19529/del_space {"space_name":"g_r14b_probe"} -> 200 {"msg":"删除成功"}
   SHOW SPACES 中**已消失**            <- 真的删了
```

代码（`graph_service.py:166-193`）：
```python

```

`rebuild_kb9_effective.py:109` 原为 `json={"space_name": "kb_9"}` →
drop 的是不存在的 `kb_9`（真实空间是 `g_kb_9`）→ **零删除 + 200 成功** →
随后 `generate_triple_data` 是追加，于是 `87 -> 91`，55 个旧代顶点与 76/126 条旧代边全部留存。

> **口径更正**：此前写成"缺了 del_space 这一步"不准确。准确说法是
> **del_space 被执行了、也返回成功，但它删的是一个不存在的空间，因此零效果**。

